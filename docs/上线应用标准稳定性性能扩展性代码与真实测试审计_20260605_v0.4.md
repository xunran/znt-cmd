### 3.1 已被代码和测试证明的稳定性改进

| 项 | 代码证据 | 测试 / 报告证据 |
| --- | --- | --- |
| HTTP timeout | `cmd/clean-core-server/main.go:59-65` 配置 `ReadHeaderTimeout/ReadTimeout/WriteTimeout/IdleTimeout` | 最新 release candidate 通过 |
| 请求体大小限制 | `internal/server/server.go:463` 包装 `withMaxBodyBytes`；`internal/server/server.go:8754-8775` 使用 `http.MaxBytesReader` | `internal/server` 测试和全量测试通过 |
| deep readiness | `internal/server/handlers_readiness.go:14-27` 在 deep 模式调用 readiness report；`internal/readiness/report.go:60-70` 做 DB ping；`internal/readiness/report.go:120-134` 做 live schema 检查 | Postgres release/upgrade 报告均为 ready |

| agent.run admission | `internal/app/core/core.go:237-240` 创建 limiter；`internal/runtime/admission/limiter.go:46-88` 实现全局/租户/Agent running limit 与 rejected 计数 | 默认 limiter 压测返回可控 429；`agent_runs_rejected_total` 可观测 |
| async run 模式 | `internal/server/server.go:5339-5354` async 下先 `PrepareEnvelopeRun`，后台 `ExecutePreparedRun`，并释放 admission slot | async 10k in-memory、async 5k Postgres 压测通过 |
| 迁移治理 | `migrations/checksums.json` 固化 checksum；`internal/storage/postgres/postgres.go:3190-3194` 已应用 migration `ON CONFLICT DO NOTHING`，不改写旧记录 | `check_migration_checksums.ps1 -ValidateOnly`、Postgres upgrade E2E 通过 |

### 3.2 仍不能称为生产高可用的原因

| 风险 | 证据 | 影响 |
| --- | --- | --- |
| 单机口径不是 HA | 本轮目标限定为单进程 + 单 Postgres 实例 | 机器宕机、Postgres 实例故障、跨节点流量切换未验证 |
| `/metrics` 未鉴权 | `internal/server/handlers_metrics.go:13-15` 直接公开 `/metrics`；`/v1/metrics/governance` 才走 `requireAuth` | 生产环境需要网关、内网限制或鉴权策略 |
| 默认仍可走 in-memory store | `internal/app/core/core.go:112-188` 只有 `DatabaseURL` 存在时才替换为 Postgres，否则大量 store 初始化为 in-memory | 本地模式不适合长期生产容量和持久化承诺 |
| 默认 `agent_run_execution_mode` 是 sync | `internal/app/config/config.go` 默认值为 `sync`；async 需要显式配置 | 生产若忘记切 async，长模型/慢工具仍会占用 HTTP 请求生命周期 |
| OpenAI-compatible streaming 是伪流式 | `internal/model/client/client.go:345-360` 的 `Stream` 调用 `Complete` 后再发事件 | 不能把当前 streaming trace 当成真实增量 token 流验证 |

稳定性结论：单机入口保护、依赖探针、连接池、背压和迁移治理已具备上线前基础；生产 HA 仍需要多副本、PDB/滚动发布、外部 DB HA、metrics 访问控制和故障演练。

### 5.2 扩展性风险

| 风险 | 证据 | 判断 |
| --- | --- | --- |
| `server.go` 仍过大 | 当前 `internal/server/server.go` 8475 行 | 已拆出 health/readiness/metrics/usage/middleware，但 API 和 command 仍集中，后续需要继续按域拆分 |

## 6. 已证明 / 未证明分层

### 已被证据证明

```text
1. 全量 Go 测试、vet、race、contract、API smoke、MMR service、all-interfaces 均通过。
2. 单机 HTTP 入口已有 timeout、panic recovery、body limit、auth、admission limiter。
3. deep /readyz 可覆盖 DB ping 和 live schema；Postgres release 和 upgrade E2E 通过。
4. 默认 limiter 可返回 429 背压，而不是无限堆积。
5. stub 模型下 in-memory 与 Postgres 路径均能完成千级到万级请求探针。
6. 独立 DeepSeek smoke 在 2026-06-05 通过。
```

### 有正面迹象但证据不足

```text
1. async agent.run 可以缩短 HTTP 生命周期，但真实长模型/慢工具/审批等待下的持续运行未验证。
2. Postgres-backed 10k sync 和 5k async 可跑通，但 DB wait 与 queue depth 已提示瓶颈。
3. 架构边界支持扩展，但 server 层和 Postgres repository 测试仍需继续拆分和补强。
```

### 明确未验证 / 阻塞

```text
1. 多副本 HA、节点故障转移、Postgres HA、PDB/HPA/滚动发布未验证。
2. 真实模型容量压测、限速恢复、长时间 soak test 未验证。
3. /metrics 生产鉴权或网络隔离未在代码中实现。
4. OpenAI-compatible 真流式未实现。
5. CLEAN_CORE_MODEL_API_KEY 若仍是模板占位符，真实模型脚本会被阻断。
```

## 8. 下一阶段达标验收矩阵

本节不是新的代码任务实现，而是把“怎样真正达到上线应用标准”拆成可验收证据。后续任何代码修改都应该按这张表逐项补证据。

| 上线标准项 | 当前状态 | 必须补齐的权威证据 |
| --- | --- | --- |
| 生产高可用 | 未达标 | 多副本或等价进程冗余配置；PDB/滚动发布/资源限额；删除单实例或进程重启时业务请求不中断的真实演练报告；Postgres HA 或明确的单点风险接受说明 |
| 生产 readiness 摘流 | 单机 deep ready 已达成，集群摘流未验证 | DB 断开、live schema 缺失、migration checksum mismatch 三类负例下，生产 probe 返回 not ready，并由流量入口停止转发的 E2E |
| `/metrics` 生产访问控制 | 未达标 | 代码鉴权、网关 ACL 或内网隔离策略；未授权访问被拒绝的集成测试；运维 runbook 写明暴露范围 |
| 成千上万智能体容量 | 未证明 | Postgres async 10k/50k 或更高阶梯压测；至少 30-60 分钟 soak；p50/p95/p99、RPS、CPU、内存、DB pool、DB wait、queue depth、错误率、拒绝率完整报告 |
| 真实模型容量 | 未证明 | 真实 provider 小流量压测；限速/429/超时恢复；模型延迟分布；成本和 token 使用量；失败重试不会拖垮 worker/queue 的报告 |
| 慢工具和审批等待 | 未证明 | 慢 ToolHost、unhealthy provider、pending approval 长时间停留场景；证明 async worker 不阻塞 HTTP，并且队列、拒绝、恢复可观测 |
| Postgres repository 单测 | 不足 | `internal/storage/postgres` 不再只有 0.3% 覆盖；核心 task/run/trace/audit/tool/package/migration repository 有 live DB 或等价测试覆盖 |
| 真流式模型 | 未实现 | `OpenAICompatibleClient.Stream` 不再包装 `Complete`；实现真实 streaming parser；有 delta 顺序、错误中断、usage/finish 事件测试 |
| server 层可持续扩展 | 部分达成 | `server.go` 继续按 command/resource 域拆分；每个 handler 域有对应测试；合约脚本持续 warning=0 |
| 生产 adapter | 部分达成 | worker/sandbox/managed 要么保持明确 disabled 并在 readiness/capability 中暴露，要么接入真实 adapter 并完成安全、资源、凭据边界测试 |

达标时的最终判定应当不是“某条命令通过”，而是每一项都有代码证据、自动化测试证据和至少一次真实运行报告。
