版本：v0.1
日期：2026-06-04
依据：`docs/智能体技术演进稳定性与解耦边界分析_v0.1.md`
定位：把架构分析带入当前代码后的证据化审查、差异修正和实施任务清单

---

## 0. 当前结论

这次代码对照的核心结论是：

```text
CleanCore 的主体方向基本符合“稳定内核 + 策略驱动 + adapter + trace/audit/replay”的架构判断。
真正需要改的不是大拆大改，而是把少数关键边界补成更强的可回放证据。
```

已经被代码证明成立的部分：

```text
1. Runtime Kernel 仍是唯一主循环控制面。
2. Task / Run 状态由领域服务推进，不由 hook / executor 直接改。
3. 模型输出必须经过 Decision parser / validator。
4. ToolRuntime 是工具执行治理入口，包含 schema / policy / approval / execution domain / trace。
5. Runtime Hook 当前是 data patch / hint / intent 模型，没有接管主循环。
6. AgentPackage 支持 draft / validate / publish / canary / stable / rollback。
7. 外部 tools.invoke 只允许调用 Agent 显式 exposed 的工具。
8. 动态工具目录已有 ToolProvider / ToolGroup / ToolManifest / RuntimeRegistry。
9. Trace / Audit / Eval / Readiness / Release report 已形成治理闭环。
```

需要修正或澄清的架构分析表述：

```text
1. CleanCore 当前没有独立 handoff DecisionType。
   内部 Agent 协作由 tool_call 调用 origin.agent.delegate 后进入 AgentHandoff。

2. CleanCore 当前 RunStatus 没有 timed_out。
   超时以 CodeModelTimeout 错误进入 failed。

3. ToolCall 治理语义中的 tool_version / approval_status / execution_domain
   并没有全部直接落在 ToolCall 结构上。
   当前分别由 ToolDefinition.Version、ToolResult.Status、ExecutionProfile/trace 表达。
```

真正需要补强的架构缺口：

```text
1. 工具调用缺少“实际执行版本和执行画像”的持久化快照。
2. Model Runtime 缺少显式 ModelCapabilityDescriptor。
3. 全路由真实 API 测试已有脚本雏形，但需要作为最终验收矩阵正式运行并产出报告。
```

## 1. 代码证据

### 1.1 Runtime Kernel

代码位置：

```text
internal/runtime/kernel/coordinator.go
```

证据：

```text
Coordinator.loop / step 负责 run 主循环、step limit、duration limit。
step 内按顺序执行 candidate retrieval、hook patch、WorkView、PromptBundle、ModelDecision、MemoryWriteIntent、dispatch。
dispatchToolCalls 统一进入 ToolRuntime.Invoke。
```

判断：

```text
文档中“不要过早开放完整 RuntimeDriver，Kernel 保持唯一控制面”的判断成立。
```

### 1.2 Decision 结构化校验

代码位置：

```text
internal/contracts/decision.go
internal/contracts/enums.go
internal/decision/parser/parser.go
internal/decision/validator/validator.go
internal/model/client/client.go
```

证据：

```text
ModelClient 返回 RawDecisionJSON。
decisionparser.Parse 将模型输出转为 contracts.Decision。
Validator.Normalize 校验 DecisionType、reply.text、tool candidate set 等。
DecisionType 当前为 reply / no_op / ask_clarification / tool_call / unsupported / error。
ReplyKind 包含 answer / refusal / policy_notice / clarification_message / status_update。
```

判断：

```text
“模型输出不能直接成为事实”成立。
原文把 handoff 写入稳定 Decision 类型不准确，已在架构分析文档修正。
```

### 1.3 ToolRuntime 治理入口

代码位置：

```text
internal/tool/runtime/runtime.go
internal/policy/toolpolicy/evaluator.go
internal/execution/domain
internal/tool/repository
```

证据：

```text
ToolRuntime.Invoke 先从 Registry 获取 ToolDefinition。
随后执行 AvailabilityChecker、input schema、ToolPolicy、approval、ExecutionDomain、output schema、trace。
高风险工具会返回 pending_approval。
Coordinator 和 ExternalTools 都先 SaveCall，再 Invoke，再 SaveResult。
```

判断：

```text
“ToolRuntime 是工具执行唯一治理入口”成立。
需要补强的是 ToolCall 对实际 tool version / execution profile 的持久化。
```

### 1.4 Runtime Hook

代码位置：

```text
internal/runtime/hook/hooks.go
internal/runtime/hook/service.go
internal/runtime/kernel/coordinator.go
```

证据：

```text
HookPoint 只有 before_context_build / after_candidate_retrieval / before_model_call / before_memory_write。
Patch 只有 add_context_blocks / drop_context_refs / tool_rank_adjustments / memory_write_intents / planner_hints。
validatePatch 禁止 hook rank denied/unapproved tool，禁止 drop policy/safety。
Coordinator 只把 patch 应用于候选、上下文、prompt 和 memory write intent。
```

判断：

```text
“Hook 只影响看见什么、怎么排序、写入建议；不能执行工具、不能推进状态”成立。
```

### 1.5 动态工具和外部工具

代码位置：

```text
internal/tool/catalog/catalog.go
internal/tool/invoke/service.go
internal/tool/registry/registry.go
internal/server/server.go
```

证据：

```text
ToolCatalogService 管理 provider / group / manifest。
static_tool_host 和 http_direct 已作为 executor adapter 存在。
external tools.invoke 先加载 AgentDefinition，再校验 tool_id 必须在 agent.Tools.ExposedToolIDs 中。
ToolRuntime.Availability = ToolCatalog，执行前再次检查 manifest/group/provider/status。
```

判断：

```text
“工具定义生命周期、运行时注册生命周期、任务调用生命周期分离”基本成立。
“外部工具不能绕过 ToolRuntime”成立。
```

### 1.6 AgentPackage / Release / Eval

代码位置：

```text
internal/agentdef/package/service.go
internal/policy/engine/engine.go
internal/eval
internal/server/server.go
```

证据：

```text
AgentPackage 支持 draft、proposal、validate、review、publish、canary、stable、rollback。
Policy 也支持 draft、publish、canary、stable、rollback。
EvalRunner 可对 package/eval suite 执行 gate。
```

判断：

```text
“行为定义进 AgentPackage，策略进 Policy，发布走 Eval / Release”成立。
```

## 2. 差异和任务裁剪

### 2.1 文档表述差异

| 项 | 文档原表述 | 代码事实 | 处理 |
| --- | --- | --- | --- |
| Handoff Decision | handoff 是稳定 Decision 类型 | 没有 handoff DecisionType，走 tool_call + origin.agent.delegate | 已修正文档 |
| timed_out 状态 | Run 生命周期包含 timed_out | 当前 RunStatus 无 timed_out，超时进入 failed | 已修正文档 |
| ToolCall 快照 | tool_version / execution_domain 属于工具调用语义 | 当前未直接持久化到 ToolCall | 进入重构任务 |

### 2.2 不作为本轮强制实现的项

下面这些项是合理未来方向，但当前代码已有可接受边界，且原架构分析也没有要求本轮必须实现完整能力：

```text
1. 独立 A2A adapter。
   当前内部协作已有 AgentHandoff，外部 Agent 协议可作为 future adapter。

2. MCP adapter。
   当前已有 static_tool_host / http_direct 的 ToolProvider adapter，
   MCP 可在 ToolProvider executor 类型扩展时接入。

3. 完整 RuntimeDriver。
   当前 Hook 模型符合文档建议，不应过早开放控制流插件。

4. 独立 timed_out 状态。
   当前 CodeModelTimeout -> failed 可以表达结果。
   是否添加独立状态需要产品/API 兼容决策，不作为本轮重构前置。
```

## 3. 任务清单

### T1. 工具调用执行快照

目标：

```text
让每一次 ToolCall 持久化记录调用时实际使用的 tool version 和 execution profile。
```

要改的文件：

```text
internal/contracts/tool.go
internal/runtime/kernel/coordinator.go
internal/tool/invoke/service.go
internal/storage/postgres/postgres.go
migrations/001_clean_core_base.sql
migrations/002_tool_call_execution_snapshot.sql
internal/tool/repository/*_test.go
internal/storage/postgres/*_test.go
```

实现要点：

```text
1. ToolCall 增加 tool_version、execution_profile 字段。
2. Coordinator 在 SaveCall 前从 ToolRuntime.Definition 读取 ToolDefinition 并写入快照。
3. ExternalTools.Invoke 在 SaveCall 前同样写入快照。
4. Postgres tool_calls 增加 tool_version / execution_profile 列。
5. toolCallSelectSQL / scanToolCall / SaveCall 全部支持新字段。
6. API /v1/tools/{tool_call_id}/trace 返回的 tool_call 能看到快照字段。
```

验收：

```text
go test ./...
脚本真实调用 tools.invoke 后，/v1/tools/{tool_call_id}/trace 中 tool_call.tool_version 非空。
```

### T2. ModelCapabilityDescriptor

目标：

```text
让 Model Runtime 显式暴露供应商、模型名、结构化输出、流式、openai-compatible、reasoning/thinking 配置等能力描述。
```

要改的文件：

```text
internal/model/client/client.go
internal/runtime/kernel/coordinator.go
internal/app/core/core.go
internal/model/client/*_test.go
```

实现要点：

```text
1. 增加 ModelCapabilityDescriptor 结构。
2. 增加可选接口 ModelCapabilityProvider。
3. StubModelClient 和 OpenAICompatibleClient 实现 Capabilities()。
4. VersionSnapshot.AdditionalAttributes 写入 model_capabilities_hash。
5. TraceModelCalled payload 可包含 model_capabilities。
```

验收：

```text
go test ./...
agent.run 后 trace 的 model.called 或 run snapshot 能看到模型能力描述/哈希。
```

### T3. 全路由真实 API 测试矩阵复核

目标：

```text
确认 docs/openapi.clean-core.v1.json 中每个操作都被真实 HTTP 请求覆盖，
而不是只靠单元测试或虚拟函数调用。
```

现有基础：

```text
scripts/e2e_clean_core_all_interfaces.ps1
```

实施要点：

```text
1. 运行 all-interfaces E2E。
2. 如果缺少 OpenAPI operation coverage，补脚本。
3. 将 tool call snapshot 字段纳入断言。
4. 保留 all-interfaces-report.json 作为最终报告证据。
```

验收：

```text
all-interfaces-report.json status = passed。
operation_count 等于 OpenAPI 操作数。
missing operations = 0。
```

### T4. 真实模型可选 smoke

目标：

```text
如果环境变量已配置真实模型 key 和 base_url，运行一次真实模型 agent.run smoke。
如果未配置或网络不可用，最终报告明确说明未执行原因。
```

现有基础：

```text
scripts/e2e_deepseek_smoke.ps1

config.example.json
```

验收：

```text
真实模型 smoke 通过，或报告中给出明确不可执行证据。
```

### T5. 最终架构符合性与真实接口测试报告

目标：

```text
输出最终报告文档，覆盖代码改动、架构符合性、单元测试、真实 API 测试、真实模型 smoke 情况。
```

建议文件：

报告必须包含：

```text
1. 对照原架构分析文档的逐项结论。

5. all-interfaces E2E 结果。

7. 真实模型 smoke 结果或未执行原因。
```


