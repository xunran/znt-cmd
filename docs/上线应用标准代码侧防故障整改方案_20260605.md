# 上线应用标准代码侧防故障整改方案

版本：v0.1  
日期：2026-06-05  
范围：CleanCore / Origin Agent Platform 当前工作区  
依据：

- `docs/上线应用标准稳定性性能扩展性代码与真实测试审计_20260605_v0.4.md`
- `docs/上线应用标准达标整改实施文档_20260605.md`
- `docs/上线应用标准整改总体验收报告_20260605.md`

说明：本文档只覆盖“除继续拆 `internal/server/server.go` 之外”的代码侧防故障整改。`server.go` 后续按资源域继续拆分仍然重要，但不纳入本文档执行范围。

---

## 1. 总体判断

当前系统已经达到受控单机 Alpha/Beta 的基础门槛：`/metrics` 鉴权、deep readiness、readiness 专用 DB 池、Postgres 30/60 分钟 soak、50k 阶梯容量、真实 SSE streaming、关键包 race、RC/E2E 都有通过证据。

但如果目标是“上线后尽量不出事故”，剩余主要风险不在单次请求处理逻辑，而在故障边界：

```text
1. async run 返回后仍依赖进程内 goroutine，进程重启可能丢失或中断后台执行。
2. 生产危险配置仍有机会启动，例如 sync run、in-memory store、关闭 metrics auth。
3. admission 只限制 run 数量，还没有按模型、ToolHost、DB 等依赖预算做背压。
4. 真实模型有格式错误和限速风险，缺 provider 级熔断、降级和恢复窗口。
5. DB wait 已是容量瓶颈，除 readiness 外，业务写入、查询、trace/audit 仍共享压力面。
6. 集群 HA、Postgres HA、真实模型并发容量仍需要外部环境验证，不能靠本地 stub 证明。
```

整改目标不是承诺“永不出故障”，而是把故障变成可拒绝、可恢复、可观测、可复盘。

---

## 2. 执行原则

```text
1. 不把单机 stub 压测当作生产 HA 或真实模型容量证明。
2. 先保护任务不丢，再优化吞吐和延迟。
3. 危险配置在生产环境必须启动失败，而不是依赖文档提醒。
4. 背压必须贴近依赖资源：模型、ToolHost、DB、队列、租户。
5. 每一项都要有代码证据、自动化测试、真实运行或可复现实验报告。
6. 未通过验收的能力只能标记为 blocked 或 risk evidence，不能标记为达标。
```

## 3. 优先级矩阵

| 编号 | 优先级 | 整改项 | 当前风险 | 目标状态 |
| --- | --- | --- | --- | --- |
| C0-1 | P0 | durable async worker | async run 返回后依赖进程内 goroutine，进程重启可能导致后台执行丢失或状态不一致 | async run 先持久化入队，由 worker lease 执行，可恢复、可重试、可观测 |
| C0-2 | P0 | 生产启动安全门禁 | 生产环境仍可能以 sync、in-memory、metrics auth disabled 等危险配置启动 | 生产危险配置直接启动失败，错误信息明确 |
| C0-3 | P0 | 依赖预算式背压 | admission 只限制 run 数，DB/model/tool 仍可能被打满 | 按依赖维度限流、排队、超时和拒绝，指标可见 |
| C1-1 | P1 | 模型 provider 熔断与恢复 | 真实模型格式错误、429、5xx 会扩散到 run 层 | retry/repair/circuit breaker/恢复探针闭环 |
| C1-2 | P1 | DB 压力分层与降级 | readiness 已隔离，但主写入、查询、trace/audit 仍可能互相抢资源 | 主链路优先，低优先级写入可延迟或降级 |
| C1-3 | P1 | 运行中任务恢复与补偿 | pending/leased/running run 在重启后缺少统一修复策略 | startup reconciler 可恢复、超时、补偿或标记失败 |
| C2-1 | P2 | 生产 HA 代码配套 | Helm 有静态基线，但代码还缺更完整的优雅摘流和关闭保障 | shutdown drain、worker stop、lease 释放和 readiness 摘流联动 |
| C2-2 | P2 | 真模型容量门禁 | 真实模型并发小样本出现格式错误 | 独立真实模型压测与限速恢复门禁，失败不影响 stub 发布门禁判断 |

## 4. C0-1 durable async worker

### 当前证据

`agent.run` async 当前路径是在 HTTP handler 中先 `PrepareEnvelopeRun`，再用后台 goroutine 调 `ExecutePreparedRun`。这证明了 HTTP 生命周期可以缩短，但没有证明进程重启、发布、panic、宿主机故障时任务不会丢。

### 架构调整

新增持久化队列层，建议放在：

```text
internal/runtime/runqueue
internal/runtime/worker
internal/storage/postgres/run_queue.go
migrations/003_agent_run_queue.sql
```

核心接口：

```go
type Store interface {
    Enqueue(ctx context.Context, item QueueItem) error
    Lease(ctx context.Context, workerID string, limit int, leaseUntil time.Time) ([]QueueItem, error)
    Heartbeat(ctx context.Context, itemID string, leaseUntil time.Time) error
    MarkCompleted(ctx context.Context, itemID string, result RunSummary) error
    MarkFailed(ctx context.Context, itemID string, failure RunFailure) error
    RequeueExpired(ctx context.Context, now time.Time, maxAttempts int) (int, error)
}
```

队列表字段建议：

```text
queue_id, tenant_id, agent_id, run_id, task_id, trace_id,
payload_json, status, priority, attempts, max_attempts,
available_at, lease_owner, lease_expires_at,
last_error_code, last_error_message,
created_at, updated_at
```

执行策略：

```text
1. HTTP async 只做 prepare + enqueue，入队成功后返回 run_id/task_id/queue_id。
2. worker 从 Postgres lease 任务，执行 `ExecutePreparedRun`。
3. worker 定期 heartbeat，执行完成后 mark completed/failed。
4. 进程启动时 requeue expired lease，超过 max_attempts 的任务转 failed 并写 trace/audit。
5. admission slot 不再覆盖整个后台生命周期，改由 worker lease 和依赖预算控制。
```

### 验收门禁

| 门禁 | 要求 |
| --- | --- |
| 单元测试 | enqueue/lease/heartbeat/complete/fail/requeue expired/idempotency |
| Postgres live test | worker A lease 后未完成，lease 过期后 worker B 可接管 |
| server 测试 | async HTTP 返回后不直接执行 goroutine，任务状态由 queue 驱动 |
| E2E | 发起 async run 后 kill server，重启后 run 最终 completed 或明确 failed，不丢失 |
| 观测 | `/metrics` 暴露 queued/leased/completed/failed/retried/expired lease |

## 5. C0-2 生产启动安全门禁

### 当前证据

生产环境已经要求 `database_url` 和 `service_token`，metrics auth 在 production `auto` 下会要求认证。但默认 `agent_run_execution_mode` 仍是 `sync`，本地无 `DatabaseURL` 会回退 in-memory store。

### 代码调整

在 `internal/app/config` 增加生产 profile 严格校验：

```text
production:
  database_url 必填
  service_token 必填
  readiness_mode 必须 deep
  metrics_auth_mode 不允许 disabled
  agent_run_execution_mode 必须 async 或 durable_async
  db_readiness_max_open_conns 必须 > 0
  db_readiness_max_idle_conns 必须 > 0
  run/tool/model timeout 必须 > 0
```

在 `internal/app/core` 增加 store mode 显式声明：

```text
CLEAN_CORE_STORAGE_MODE=memory|postgres
```

生产环境只允许 `postgres`。本地默认可以继续 `memory`，但 `/v1/readiness/report` 要明确暴露 `storage_mode=memory` 和 `production_ready=false`。

### 验收门禁

| 门禁 | 要求 |
| --- | --- |
| config 单测 | 每个危险配置都有明确错误 |
| server 启动测试 | production + memory/sync/metrics disabled 启动失败 |
| Helm 静态校验 | values 默认满足生产门禁 |
| RC | release candidate 包含 production config validation |

## 6. C0-3 依赖预算式背压

### 当前证据

现有 admission limiter 能限制 run 并返回 429，60 分钟 soak 证明 DB wait 可观测。但容量瓶颈来自依赖资源竞争，不只是 run 总数。

### 代码调整

在 `internal/runtime/admission` 或新包 `internal/runtime/budget` 增加资源预算：

```text
global_run_budget
tenant_run_budget
agent_run_budget
model_provider_budget
tool_provider_budget
db_write_budget
queue_depth_budget
```

预算行为：

```text
1. 超过硬上限直接 429 / ADMISSION_REJECTED。
2. 超过软上限进入短等待队列，超过 queue_wait_timeout 后拒绝。
3. provider unhealthy 或 circuit open 时快速失败，不进入长队列。
4. DB wait、queue depth、provider error rate 可触发动态降载。
```

### 验收门禁

| 门禁 | 要求 |
| --- | --- |
| 单测 | 每类 budget acquire/release/reject/stats |
| server 测试 | model/tool/db budget 满时返回可解释 429 或 503 |
| perf | 高并发下 rejected 增加但 failed=0，p99 不无限上升 |
| metrics | 暴露各类 budget running/queued/rejected/wait_ms |

## 7. C1-1 模型 provider 熔断与恢复

### 当前证据

真实 DeepSeek 小并发曾出现 `model response did not contain a decision`。kernel 已有 repair attempt 和 retryable model error 机制，但 provider 级熔断、恢复探针和限速窗口还不完整。

### 代码调整

新增 provider runtime state：

```text
provider_id, state=open|half_open|closed,
failure_count, rate_limited_count, invalid_response_count,
opened_at, next_probe_at, last_success_at
```

处理策略：

```text
1. 429/timeout/5xx 按 retryable 退避重试。
2. invalid_provider_response 先走一次 repair；连续失败计入 provider health。
3. circuit open 时新 run 快速失败或转备用 provider。
4. half_open 只允许少量探针，成功后关闭熔断。
5. 熔断状态进入 readiness report 的 capability 区域，但不一定使整个服务 not_ready。
```

### 验收门禁

| 门禁 | 要求 |
| --- | --- |
| model client 单测 | 429/5xx/timeout/invalid response 分类准确 |
| kernel 单测 | repair 成功、repair 失败、retry exhausted、circuit open |
| E2E | mock provider 连续 429 后 circuit open，新请求快速失败，恢复探针成功后恢复 |
| real model smoke | 小流量真实模型报告包含 rate_limit/error/recovery/token/cost |

## 8. C1-2 DB 压力分层与降级

### 当前证据

readiness 专用 DB 池已经解决了业务池饱和导致 readiness 偶发 `not_ready` 的问题。但 50k 和 60 分钟多租户报告仍显示 DB wait 明显。

### 代码调整

在存储层区分主链路和低优先级写入：

```text
critical: run/task/tool approval/package 状态
important: trace/audit/replay evidence
best_effort: usage samples、diagnostic details、large payload snapshots
```

建议机制：

```text
1. critical 写入使用主 DB pool，并有严格超时。
2. important 写入可进入异步 outbox，失败后重试。
3. best_effort 写入允许采样、截断或降级。
4. 慢 SQL 和 DB wait 超阈值时，先降级 best_effort，再拒绝新 run。
```

### 验收门禁

| 门禁 | 要求 |
| --- | --- |
| 单测 | critical 写失败会使 run 失败；best_effort 写失败不影响 run 完成 |
| Postgres live test | outbox 重试、幂等、截断、清理 |
| perf | DB wait 高时主链路 failed=0，best_effort 降级计数增加 |
| metrics | `db_write_critical_*`、`outbox_*`、`best_effort_dropped_total` |

## 9. C1-3 运行中任务恢复与补偿

### 当前证据

当前 readiness、trace、audit、replay 能解释链路，但对进程重启时处于 running/pending/leased 的 run，还需要统一恢复策略。

### 代码调整

新增 reconciler：

```text
internal/runtime/recovery
```

恢复规则：

```text
queued + available_at <= now: 可执行
leased + lease_expires_at < now: requeue 或 failed
running + no heartbeat: 根据 run 类型 requeue 或 failed
waiting_approval: 保留，不自动失败
terminal: 不处理
```

### 验收门禁

| 门禁 | 要求 |
| --- | --- |
| 单测 | 每种状态恢复规则覆盖 |
| Postgres live test | 构造 stale running/leased，启动 reconciler 后状态正确 |
| E2E | kill/restart 后没有永久 running 的 run |
| replay | 恢复动作写入 trace/audit，可解释 |

## 10. C2-1 生产 HA 代码配套

### 当前证据

Helm 已有 2 副本、PDB、rolling update、resources、probe 的静态基线，但当前环境没有真实 K8s 演练，也没有 Postgres HA。

### 代码调整

补齐优雅摘流和关闭：

```text
1. SIGTERM 后 readiness 立即进入 draining。
2. HTTP 停止接收新 agent.run。
3. worker 停止 lease 新任务，等待当前任务 heartbeat/complete 或释放 lease。
4. 超过 shutdown grace 后未完成任务由 lease 过期恢复。
5. `/v1/readiness/report` 暴露 draining、worker_stop、inflight_runs。
```

### 验收门禁

| 门禁 | 要求 |
| --- | --- |
| 单元测试 | drain 状态下新 run 被拒绝，healthz 可继续响应 |
| E2E | 发起长 run 后 SIGTERM，重启后任务可恢复 |
| K8s 演练 | 删除 Pod / rolling update 期间请求不中断或被可解释拒绝 |
| 文档 | runbook 记录 grace period、恢复窗口和失败判定 |

## 11. C2-2 真模型容量门禁

### 当前证据

真实 DeepSeek 串行 5/5 通过，但并发 2 / 10 曾出现 1 个模型格式错误。不能把 stub 50k/60 分钟 soak 外推为真实模型容量。

### 代码与脚本调整

增强 `scripts/perf_real_model_agent_run.ps1`：

```text
1. 支持并发阶梯：1、2、5、10。
2. 支持限速恢复窗口：429 后暂停、探针、恢复。
3. 报告 provider_error_kind、repair_success、circuit_state、token、cost。
4. 真实 API key 永不落盘，只记录 provider/model/usage。
```

### 验收门禁

| 门禁 | 要求 |
| --- | --- |
| validate-only | 无凭据也能校验脚本结构 |
| mock provider | 429/5xx/invalid JSON/slow response 场景通过 |
| real provider | 有凭据时运行小流量报告，失败则保持 boundary，不阻塞 stub RC |
| 报告 | 明确成本、token、错误、恢复，不使用 stub 替代 |

## 12. 不纳入本文档的事项

| 项 | 原因 |
| --- | --- |
| 继续拆 `internal/server/server.go` | 用户本轮明确排除；后续可单独按 API domain 规划 |
| Postgres HA 架构选型 | 需要外部环境或运维决策，代码侧只能配合 readiness/drain/recovery |
| 真实 K8s 删除 Pod 演练 | 当前没有可用目标集群，需外部环境 |
| 更高阶硬件容量调优 | 需要固定机器规格、DB 参数和成本目标，否则结果不可复用 |

## 13. 推荐执行顺序

```text
1. C0-1 durable async worker
2. C0-2 生产启动安全门禁
3. C0-3 依赖预算式背压
4. C1-1 模型 provider 熔断与恢复
5. C1-2 DB 压力分层与降级
6. C1-3 运行中任务恢复与补偿
7. C2-1 生产 HA 代码配套
8. C2-2 真模型容量门禁
```

第一阶段完成标准：

```text
C0-1/C0-2/C0-3 全部 verified；
release candidate passed；
Postgres async 60 分钟 5 租户 soak passed；
kill/restart async run E2E passed；
生产危险配置启动失败测试 passed。
```

达到第一阶段后，系统可以更有底气进入受控小规模试点；但仍不能对外宣称完整生产 HA 或真实模型成千上万智能体容量，除非 C2 外部演练也完成。
