## 0. 总结结论

本轮结论必须分三层看：

| 维度 | 当前结论 | 是否达到上线应用标准 |
| --- | --- | --- |
| 稳定性 / 高可用 | 功能稳定性、治理闭环、Postgres 持久化、真实模型 smoke、race test 均有证据；但部署高可用、连接池、探针、请求限流/超时、迁移治理仍有硬缺口。 | 未完全达到生产 HA 标准 |
| 性能 / 成千上万智能体 | 单机 stub 内存压测 1000 请求全成功；Postgres-backed 500 请求全成功。但没有 1 万级 Agent/Run 压测、没有 p95/p99/资源曲线、没有队列/背压/调度器证据。 | 未证明可支撑成千上万智能体生产运行 |
| 后续扩展 / 架构演进 | contracts、model/tool/runtime hook/execution domain/agent package/eval/release 边界较清晰，适合扩展；但 `server.go` 过大、部分 adapter 仍是未来态，部分命令缺直接测试证据。 | 基本满足扩展方向，但需要工程化收口 |

最终判断：

```text
当前代码可以支撑受控试点、内测、低到中等并发的 Alpha/Beta 级上线验证。
不建议直接宣称已经达到高可用生产和成千上万智能体规模上线标准。
```

## 2. 稳定性和高可用审计

### 2.1 已经具备的稳定性基础

代码证据：

```text

  production 环境强制要求 database_url、service_token、model_base_url、model_name。

internal/runtime/kernel/coordinator.go
  Runtime Kernel 控制 run/task 主循环、step limit、duration limit、tool limit、decision parse/validate、trace 写入。

internal/tool/runtime/runtime.go
  ToolRuntime 统一执行 schema、policy、approval、execution domain、credential/data boundary、trace/audit。

internal/storage/postgres/postgres.go
  Postgres repository 覆盖 task、run、trace、audit、tool、package、eval、knowledge 等核心事实。

internal/task/repository/memory.go 和 internal/storage/postgres/postgres.go
  Task 更新有 version 乐观锁，Postgres 的 task + event 支持事务写入。

internal/release/report.go
  go/no-go 聚合 readiness、migration、contract、observability 和生产 gate。
```

测试证据：

```text

Postgres release E2E passed, restart 后 trace/eval 仍可读
MMR service E2E 18 个场景 passed
DeepSeek real model smoke passed
```

判断：功能稳定性和运行治理链路是当前代码最强的部分。

### 2.2 高可用缺口

| 缺口 | 证据 | 影响 |
| --- | --- | --- |
| 默认部署单副本 | `deploy/helm/clean-core/values.yaml:6` 为 `replicaCount: 1`，`deploy/helm/clean-core/templates/deployment.yaml:6` 直接使用该值 | App 层存在单点故障，不能称为高可用 |
| K8s readiness probe 只打 `/readyz` | `deployment.yaml:26-28` 使用 `/readyz`；`server.go:75-87` 的 `/readyz` 只看 `cfg.Readiness` | DB 断开、迁移异常时，K8s 探针不一定摘流 |
| 更完整 DB 检查在 `/v1/readiness/report`，但未用于探针 | `server.go:499-500` 暴露 readiness report；`internal/readiness/report.go:62-68` 会 `DB.PingContext` | 运维可查，但流量入口不自动保护 |
| DB 连接池没有显式配置 | `internal/storage/postgres/postgres.go:58-67` 只有 `sql.Open` + `PingContext`；全文未见 `SetMaxOpenConns/SetMaxIdleConns/SetConnMaxLifetime/SetConnMaxIdleTime` | 高并发时可能连接数失控或连接复用不足 |
| HTTP server 只有 `ReadHeaderTimeout` | `cmd/clean-core-server/main.go:59-62` 只配置 `ReadHeaderTimeout`，未见 `ReadTimeout/WriteTimeout/IdleTimeout` | 慢请求、长响应、连接占用风险 |
| 请求体没有全局大小限制 | `internal/server/server.go:122/541/621/748/787/825/5286` 多处直接 `json.NewDecoder(r.Body).Decode`，未见 `MaxBytesReader` | 大请求可能放大内存和 CPU 压力 |
| agent.run 是同步 HTTP 执行 | `internal/server/server.go:5373-5391` 的 `dispatchCommand` 在 HTTP 请求内直接调用 `Coordinator.HandleEnvelope` | 长任务会占用 HTTP 连接和 goroutine，缺少队列/背压 |
| 迁移 checksum 曾在现有卷上冲突 | compose 旧卷运行 `e2e_postgres_release` 出现 `001 checksum mismatch` | 需要迁移不可变和升级治理，否则老环境会阻断发布 |

高可用结论：

```text
当前具备可观测、可回滚、可持久化、可审计的稳定内核。
但生产高可用还需要部署和入口保护层硬化，尤其是 readiness、连接池、超时、限流、队列和迁移治理。
```

## 3. 性能和成千上万智能体审计

### 3.1 已有性能信号

本轮真实 HTTP 压力探针：

```text
stub + in-memory:
  total_requests = 1000
  batch_concurrency = 100
  success = 1000
  failed = 0
  requests_per_second = 2682.66

stub + Postgres:
  total_requests = 500
  batch_concurrency = 50
  success = 500
  failed = 0
  requests_per_second = 55.42
```

解释：

```text
in-memory 结果证明当前 runtime/HTTP/stub 模型路径很轻。
Postgres 结果更接近生产，但本地 55.42 req/s 只能说明基本并发可用，不能证明万级 Agent 规模。
```

### 3.2 不能宣称万级达标的原因

| 问题 | 代码/测试证据 | 影响 |
| --- | --- | --- |
| 没有 benchmark | `rg -n "func Benchmark|Benchmark[A-Z0-9_]" . --glob '!tmp/**'` 无结果 | 缺少可重复的包级性能基线 |
| 没有 1 万级 run/agent 负载报告 | 现有 E2E 是功能矩阵；本轮只跑到 1000 stub / 500 Postgres | 不能证明成千上万智能体生产运行 |
| 没有 p95/p99 和资源曲线 | 压力探针只记录吞吐和成功率 | 无法判断尾延迟、CPU、内存、DB 连接消耗 |
| agent.run 同步执行 | `internal/server/server.go:5373-5391` 在 HTTP 请求内执行模型、工具、trace、task 状态推进 | 大量长任务会占用连接和 goroutine |
| tool_calls 在单个 decision 内顺序执行 | `internal/runtime/kernel/coordinator.go:1075-1086` 对 `calls` 顺序循环，`1183-1191` 同步调用 `ToolRuntime.Invoke` | 多工具/多 Agent 编排吞吐受限 |
| Postgres 连接池未配置 | 未见连接池上限和生命周期配置 | 高并发下 DB 可能成为不可控瓶颈 |
| 内存实现大量 O(n) 扫描 | trace/audit/memory/knowledge 等 in-memory store 多为全量扫描 | 本地模式不适合高规模生产，生产必须走 Postgres/外部索引 |

性能结论：

```text
当前代码通过了基本并发烟测，但没有达到“成千上万智能体运行”的证据标准。
要达到该标准，需要正式容量测试、异步任务队列、背压、连接池、资源配额、水平扩容和监控指标闭环。
```

## 5. 上线标准差距清单

### P0：上线前必须补齐

1. K8s `replicaCount >= 2`，并增加 PDB、resource requests/limits、滚动发布策略说明。
2. 将生产探针改为能覆盖 DB 和 live schema 的 readiness，或新增轻量 `/readyz` 深度模式。
3. 配置 DB 连接池：MaxOpenConns、MaxIdleConns、ConnMaxLifetime、ConnMaxIdleTime。
4. 增加 HTTP `ReadTimeout/WriteTimeout/IdleTimeout` 和请求体大小限制。
5. 增加全局并发限制、租户级/Agent 级限流、工具调用限流和背压。
6. 建立迁移不可变治理：已应用 migration 不允许改 checksum；新增变更必须新 migration。
7. 形成正式容量测试报告：至少覆盖 1k、5k、10k agent/run，并记录 p50/p95/p99、CPU、内存、DB 连接、错误率。

### P1：规模化运行前应补齐

1. 将长任务从同步 HTTP 请求迁移到队列/worker/状态查询模式。
2. 建立 benchmark：kernel step、prompt build、tool runtime、Postgres repository、trace/audit 写入。
3. 对 Postgres-backed 压测补真实模型限速场景、工具宿主慢响应场景、审批等待场景。
4. 把 `server.go` 按资源域或 command 域拆分，降低后续扩展风险。
5. 将 contract warning 中缺少直接测试证据的 command 补成自动化覆盖。
6. 对 worker/sandbox/managed execution domain 接入真实 adapter 或明确禁用策略。

## 6. 当前 Go / No-Go

| 场景 | 建议 |
| --- | --- |
| 本地开发、演示、内测 | Go |

## 7. 后续达标验收门禁

本节不是当前已达标声明，而是把“如何从 No-Go 变成 Go”写成可验收证据。后续只要开始改业务代码或部署配置，就应逐项补证据，不能只看单个 `go test` 通过。

### 7.1 必须补齐的上线证据

| 门禁 | 当前缺口 | 达标证据要求 |
| --- | --- | --- |
| 应用层 HA | Helm 默认单副本 | `replicaCount >= 2`、PDB、requests/limits、滚动发布策略落库；实际集群或等价环境证明单 Pod 删除/重启时服务不中断 |
| 生产 readiness 摘流 | `/readyz` 未覆盖 DB/live schema | DB 正常时 `/readyz` 或生产 probe 返回 ready；DB 断开、migration 不完整、checksum 异常时返回非 ready；E2E 覆盖这三种负例 |
| DB 连接池治理 | 无显式连接池配置 | 配置项、默认值、单元测试、启动日志或 metrics 能证明 MaxOpenConns/MaxIdleConns/ConnMaxLifetime/ConnMaxIdleTime 生效 |
| HTTP 入口保护 | 缺 Read/Write/Idle timeout 和 body limit | 单元/集成测试覆盖慢请求、大请求、正常请求；大请求被明确拒绝，不进入业务 decode |
| 并发限流和背压 | 同步 `agent.run`，缺全局/租户/Agent 级背压 | 达到并发上限时返回可预期错误或排队状态；长任务不长期占用 HTTP 请求；队列长度、拒绝数、等待时长可观测 |
| 成千上万智能体容量 | 只有 1000 stub / 500 Postgres 探针 | 正式容量报告至少覆盖 1k、5k、10k run/agent，包含 p50/p95/p99、吞吐、错误率、CPU、内存、DB 连接、队列深度、模型限速和工具慢响应场景 |
| Benchmark 基线 | 无 Go benchmark | `kernel step`、`prompt build`、`tool runtime`、`Postgres repository`、`trace/audit write` 均有 benchmark，CI 保存趋势 |
| 迁移治理 | 旧卷出现 checksum mismatch | 已应用 migration 不可变策略、老环境升级演练、checksum mismatch 的阻断和恢复 runbook 均有自动化或演练记录 |
| 合约和命令测试 | 28 个 command 缺 `server_test` 直接证据 | `verify_contracts.ps1` warning 归零，或每个 warning 有等价覆盖证明并被脚本识别 |
| 架构扩展收口 | `server.go` 9055 行、部分 adapter 未来态 | API/command 分发按域拆分；worker/sandbox/managed adapter 要么真实接入并测试，要么明确禁用并在 contract/readiness 中体现 |
