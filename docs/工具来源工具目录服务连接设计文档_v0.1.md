# 工具来源、工具目录与服务连接设计文档 v0.1

## 0. 本轮审计结论

结合当前 Go 代码和 OpenAPI 后，本文档需要坚持四个硬边界：

- CleanCore 当前已真实实现 `ToolProvider`、`ToolManifest`、`ToolRuntime`、Agent `tool_bindings`、Agent `exported-tools`；`ServiceConnection` 主要存在于 `docs/openapi.yaml` 产品契约中，Go 服务端尚未完整落地。
- 当前 `http_direct` 仍是 `executor.url + method + headers` 模型，`validateManifest` 会要求 `executor.url`。本文档中的 `service_connection_id + method/path` 是目标态，不是当前已实现能力。
- 目标态建议删除原始 URL 创建能力，不做“服务连接模式/直接 URL 模式”两套长期分支。历史 URL 数据只作为迁移输入。
- `ToolProvider` 和 `ServiceConnection` 都可能导向 `ToolManifest`，但层级不同：`ToolProvider` 是工具清单同步来源，`ServiceConnection` 是连接资产和工具生成依赖，不是第二个 `ToolProvider`。

本轮重构后的推荐模型：

```text
ServiceConnection
  只管连接资产：base_url / auth_ref / network_scope / health / resources
        |
        | 被引用
        +--> ToolProvider
        |      管 catalog 同步和 provider 级执行
        |      sync -> ToolManifest
        |
        +--> ToolManifest
               HTTP API / database_query 等工具直接引用连接资产

ToolManifest
  是 Agent 最终绑定和运行时调用的唯一工具单元
```

## 1. 背景

当前前端同时出现了“工具”“企业工具服务”“服务连接”“AgentPlugin Service 接入”“ToolHost”“HTTP Direct”等概念，用户会自然产生几个疑问：

- 工具到底是企业提供的能力，还是智能体自己的能力？
- 服务连接和企业工具服务是不是同一个东西？
- HTTP Direct 应该放在服务连接里，还是工具来源里？
- Agent 创建时到底应该绑定工具服务、工具目录，还是具体工具？

这份文档给出一个统一边界：**服务连接管连接，工具来源管同步/执行工具目录，工具目录管可调用能力，Agent 只绑定具体工具权限**。

## 2. 结论摘要

| 概念 | 一句话定义 | 创建后产生什么 | 是否直接给 Agent 使用 |
| --- | --- | --- | --- |
| 服务连接 | 外部系统的 endpoint、认证、网络、健康检查、资源发现配置 | `ServiceConnection` | 否 |
| 工具来源 | 能暴露工具清单并执行工具调用的 Provider | `ToolProvider`，同步出多个 `ToolManifest` | 否 |
| 工具目录 | 平台内被治理、可测试、可授权的具体工具清单 | `ToolManifest` | 是，Agent 绑定 `tool_id` |
| Agent 工具绑定 | 某个 Agent 能用哪些工具的授权配置 | `tool_bindings` | 是 |
| Agent 对外导出工具 | 把某个 Agent 的能力包装成工具 | `ToolManifest(executor=agent_tool)` | 可被其他 Agent 绑定 |

关键口径：

- **服务连接不是工具**。它只是连接资产，例如 HTTP API、数据库、Webhook、Origin API、OAuth、缓存、队列、存储。
- **工具来源不是单个工具**。它是能够同步工具目录并执行工具调用的服务，例如 ToolHost、AgentPlugin Service、MCP Server。
- **工具目录里的 ToolManifest 才是 Agent 可绑定的东西**。
- **HTTP Direct 不是工具来源**。它是 HTTP API 工具的底层 executor；目标态要求 HTTP API 工具必须引用 HTTP API 服务连接，不保留直接填写 URL 的产品入口。
- **数据库查询能力不是服务连接本身**。数据库服务连接只证明能连上库；真正给 Agent 用的应是由连接生成/注册出来的查询工具。

## 3. 当前后端代码对齐

当前 Go 后端里，“工具来源”和“工具目录”已经有比较明确的模型，“服务连接”主要存在于产品 OpenAPI 契约中，CleanCore 代码侧还不是完整落地形态。

### 3.1 已落地

| 后端对象 | 代码位置 | 含义 |
| --- | --- | --- |
| `ToolProvider` | `internal/tool/catalog/catalog.go` | 工具来源/Provider，当前支持 `static_tool_host`、`mcp` |
| `ToolManifest` | `internal/tool/catalog/catalog.go` | 工具目录里的具体工具，包含 `tool_id`、schema、risk、visibility、executor |
| `ExecutorSpec` | `internal/tool/catalog/catalog.go` | 工具执行方式，当前支持 `http_direct`、`static_tool_host`、`mcp`、`agent_tool` |
| `ToolRuntime` | `internal/tool/runtime/runtime.go` | 工具运行时，调用前校验 input schema，调用后校验 output schema |
| Agent `tool_bindings` | `internal/server/handlers_agent_tool_bindings.go` | Agent 可用工具授权，不负责创建工具 |
| Agent `exported-tools` | `internal/server/handlers_agent_exported_tools.go` | 把 Agent 能力同步为工具目录里的 `agent_tool` |

### 3.2 产品契约已有但 CleanCore 未完整实现

`docs/openapi.yaml` 中已有 `/v1/service-connections` 相关接口和 `ServiceConnection` schema，类型包括：

- `clean-core`
- `toolhost`
- `http`
- `http-api`
- `database`
- `webhook`
- `oauth`
- `cache`
- `queue`
- `storage`

上面是当前产品契约里出现过的类型列表，不等于推荐前端都放在“服务连接”创建页。尤其 `toolhost` 更适合迁到“工具来源”，否则会和 ToolProvider 页面重复。

但当前 CleanCore Go 服务端没有同等完整的 service-connections handler/store。因此前端如果直接按这个页面做，需要明确它是 Host/PloyKit 层能力，还是下一步要在 CleanCore 补实现。

### 3.3 关键缺口

- 缺少 CleanCore 原生 `ServiceConnection` 存储和 handler。
- `ToolProvider` 暂未通过 `service_connection_id` 复用服务连接。
- `http_direct` executor 当前仍有直接 URL 配置，需要迁移为“HTTP API 服务连接 + method/path”的组合模式，并从公开 API 中删除原始 URL 创建能力。
- 暂无 `database_query` executor；数据库查询工具应通过 ToolHost/MCP 包装，或后续新增专门 executor。
- MCP 输出现在会把 `structuredContent` 包在输出对象里；若产品希望 output schema 直接描述业务对象，需要增加归一化策略。

### 3.4 代码现状与目标态差异

| 模块 | 当前代码现状 | 目标态 |
| --- | --- | --- |
| `ToolProvider` | 字段包含 `endpoint`、`auth_ref`、`timeout_ms`、`retry_max`；支持 `static_tool_host`、`mcp` | 增加 `service_connection_id`，endpoint/auth/network 从服务连接解析 |
| `ToolManifest.executor=http_direct` | `validateManifest` 要求 `executor.url`，`HTTPExecutor` 直接请求该 URL | 要求 `service_connection_id + method + path`，执行时由服务连接解析 base_url/auth/network |
| OpenAPI `ToolExecutorSpec` | `docs/openapi.clean-core.v1.json` 暴露 `url/method/headers` | 移除公开 `url`，新增 `service_connection_id`、`path`、request/response mapping |
| `output_schema` | Go 结构字段为可选，`jsonschema.ValidateObject` 对空 schema 会放过 | 目标态建议工具启用前必须有明确 `output_schema`，至少是 `{ "type": "object" }` |
| ServiceConnection | `docs/openapi.yaml` 有产品契约，CleanCore Go 端未完整实现；枚举里仍含 `toolhost` | 明确归属；若归 CleanCore，需要新增 store/handler/health/resources，并将 `toolhost` 从服务连接类型迁到工具来源语义 |
| 工具来源 OpenAPI 枚举 | `docs/openapi.yaml` 中工具来源相关枚举仍含 `http`、`http-direct` | 工具来源只保留 AgentPlugin/ToolHost/MCP；HTTP API 工具归工具目录创建 |
| 数据库查询工具 | 没有 `database_query` executor | 短期由 ToolHost/MCP 包装，长期新增受控 `database_query` |
| MCP 输出 | executor 返回 `{ structuredContent, content }` 包装对象 | 明确 output schema 描述包装对象，或新增归一化策略 |

## 4. 领域模型

推荐模型如下：

```text
ServiceConnection
  管 endpoint / auth_ref / network / health / resources
  例如 HTTP API、Database、Webhook、Origin API
        |
        | 被引用，复用连接、认证、网络边界
        +----------------------------+
        |                            |
        v                            v
ToolSource / ToolProvider        ToolGenerator
  管工具清单同步、Provider 健康、     管“从连接生成工具”的流程
  Provider 级治理                   例如 HTTP API 工具、数据库查询工具
  例如 AgentPlugin Service、         |
  ToolHost、MCP Server              |
        |                            |
        | sync catalog               | create/generate
        +-------------+--------------+
                      v
ToolCatalog / ToolManifest
  管具体工具的 schema、risk、visibility、executor、版本、测试
  例如 customer.lookup、ticket.create、db.query_orders
        |
        | allow / deny / bind tool_id
        v
Agent tool_bindings
  管某个 Agent 能用哪些工具
        |
        v
ToolRuntime
  校验输入 -> 执行工具 -> 校验输出 -> 审计追踪
```

### 4.1 工具来源和服务连接不是两个工具来源

服务连接不是第二个工具来源。它和工具来源是上下游/依赖关系：

- **服务连接**解决“怎么连到一个外部系统”，例如 base_url、认证、网络范围、健康检查。
- **工具来源**解决“从哪里同步一批工具，以及这些工具由谁执行”，例如 ToolHost、AgentPlugin Service、MCP Server。
- **工具目录**解决“平台里最终有哪些可授权调用的具体工具”。

工具来源可以引用服务连接，但服务连接不会因此变成工具来源。例子：

```text
HTTP API 服务连接
  -> 被 HTTP API 工具引用
  -> 生成 ToolManifest

HTTP API 服务连接
  -> 被 ToolProvider 引用
  -> ToolProvider 同步工具清单
  -> 生成多个 ToolManifest
```

因此，“工具来源中的工具”不会出现在服务连接中作为工具清单管理。它们只应该出现在工具目录中。服务连接详情页最多展示只读的“被引用对象”，例如被哪个 ToolProvider 引用、被哪些 HTTP API 工具引用，方便追踪影响范围。

注意：即使 ToolProvider 需要复用连接资产，服务连接也应保持通用连接语义，例如 `http-api`、`oauth`、`database`。不要把 `toolhost` 做成服务连接里的业务类型；ToolHost、AgentPlugin、MCP 这些语义应由 `ToolProvider.provider_type` 或工具来源页面表达。

更准确的说法是：服务连接管理和创建的是**接口型连接资产**，这些连接资产可以被“工具化”。例如 HTTP API 服务连接本身不是工具，但可以基于它创建一个或多个 HTTP API 工具：

```text
HTTP API 服务连接
  -> customer.lookup
  -> ticket.create
  -> order.refund
```

从 Agent 视角看，Agent 不关心这些工具背后来自 ToolHost、MCP、Agent 导出，还是 HTTP API 服务连接。Agent 只看到工具目录里的 `ToolManifest`，并通过 `tool_id` 获得授权。

所以“服务连接是不是工具提供者”要分两层回答：

- 业务语义上：可以说它是某些工具能力的上游连接来源。
- 产品/代码模型上：不要把它定义成 `ToolProvider` 或工具来源；它只是被 `ToolManifest` 或 `ToolProvider` 引用的连接资产。

### 4.2 为什么要分层

如果不分层，会出现两个问题：

- 一个 HTTP API 既像服务连接，又像工具，又像工具来源，页面和接口都会重复。
- Agent 绑定“企业工具服务”太粗，会导致一个服务里的所有工具是否都能被 Agent 使用变得不清楚。

分层后，每个问题都有唯一归属：

- 连接是否可用：看服务连接。
- 一个 Provider 是否能同步工具清单：看工具来源。
- 一个具体 operation 能不能被调用：看工具目录的 ToolManifest。
- 某个 Agent 是否能调用它：看 Agent 的 tool bindings。

## 5. 页面设计

### 5.1 左侧导航建议

建议把当前“构建/连接/运行”保留，但调整命名和职责：

```text
构建
  智能体
  技能
  工具目录

连接
  工具来源
  服务连接

运行
  运行记录
  待审批
  追踪与审计
```

命名建议：

- 当前“工具”建议改成 **工具目录**。
- 当前“企业工具服务”建议改成 **工具来源**。
- 当前“服务连接”保留，但只放连接资产，不放 ToolHost/AgentPlugin/MCP 的接入编排。

### 5.2 服务连接页面

定位：统一管理外部系统连接，不直接创建 Agent 可调用工具。

应该放：

- HTTP API 连接
- 数据库连接
- Webhook 连接
- Origin API / CleanCore 连接
- OAuth / Secret 引用
- 缓存、队列、存储连接

主要能力：

- 新建连接
- 测试连接
- 健康检查
- 认证引用/密钥轮换
- 网络访问范围
- 权限范围
- 资源发现，例如数据库表、API base path、Webhook topic
- 启用/禁用
- 审计

不应该放：

- AgentPlugin Service 接入向导
- ToolHost 工具目录同步
- MCP tools/list 同步
- 完整的 HTTP API 工具创建表单
- Agent 工具绑定

服务连接页面的结果是：

```text
connection_id
connection_type
endpoint/base_url
auth_ref
network_scope
health_status
resource_index
```

服务连接可以被工具来源或工具目录引用，也可以作为创建 HTTP API 工具的起点，但它本身不是工具，不能直接绑定给 Agent。

HTTP API 工具可以“从服务连接发起创建”，但不能“归属于服务连接管理”。也就是说，服务连接详情页可以有一个快捷动作：

```text
服务连接详情 -> 创建 HTTP API 工具
```

这个动作只是打开工具目录的新建工具流程，并预填当前 `service_connection_id`。保存后产生的仍然是工具目录里的 `ToolManifest`，工具 schema、启用状态、测试、授权和审计仍由工具目录管理。

HTTP API 服务连接的主创建入口在这里：

```text
左侧导航：连接 -> 服务连接 -> 新建服务连接 -> 类型选择 HTTP API
```

工具目录的新建 HTTP API 工具页可以提供“新建服务连接”快捷入口，但它应该是跳转、弹窗或抽屉式创建服务连接，创建成功后回填 `service_connection_id`。连接定义仍归服务连接页面管理，不归工具表单管理。

### 5.3 工具来源页面

定位：管理“能提供一批工具”的 Provider。

应该放：

- AgentPlugin Service 接入
- ToolHost 接入
- MCP Server 接入
- 工具目录同步
- Provider 健康检查
- Provider 级别启用/禁用
- Provider 级别权限、风险、调用策略

不应该放：

- HTTP API 工具创建
- 数据库连接本身
- 普通 REST API 连接本身
- 单个工具的 schema 编辑
- Agent 绑定工具

推荐来源类型：

| 来源类型 | 后端映射 | 说明 |
| --- | --- | --- |
| AgentPlugin Service | `ToolProvider(provider_type=static_tool_host)` 或兼容模式 | 企业按平台协议实现的工具服务，可通过 well-known/catalog 同步 |
| ToolHost | `ToolProvider(provider_type=static_tool_host)` | 标准工具宿主，负责目录同步和执行 |
| MCP Server | `ToolProvider(provider_type=mcp)` | 通过 MCP `tools/list` 同步，通过 `tools/call` 执行 |

ToolHost 不应该移动到服务连接中。目标态里 ToolHost 可以引用一个 HTTP API 服务连接来复用 endpoint/auth/network，但产生工具清单的仍然是 ToolProvider：

```text
HTTP API 服务连接
  -> ToolProvider(provider_type=static_tool_host, service_connection_id=...)
  -> SyncProviderCatalog
  -> 多个 ToolManifest
```

不是：

```text
HTTP API 服务连接
  -> 多个 ToolManifest
```

工具来源创建成功后，不代表 Agent 已经能使用这些工具。它只代表平台发现了一批候选工具，后续还要进入工具目录治理，再由 Agent 绑定具体 `tool_id`。

Schema 处理原则：

- 接入 ToolHost、AgentPlugin Service、MCP Server 时，不应要求用户在平台页面手写每个工具的 schema。
- 工具服务必须在 catalog / `tools/list` 中声明 `input_schema` 和 `output_schema`，平台负责同步、校验、预览和治理。
- 接入页可以允许管理员修正描述、风险等级、可见性、标签、审批策略，但不建议在这里编辑真实 schema。
- 如果同步来的 schema 不合法或缺失，工具应停留在 `validation_failed` 或 `draft` 状态，提示回工具服务修复。
- 只有 HTTP API 工具、手动导入 manifest、Agent 导出、数据库查询模板生成这类“平台内创建具体工具”的场景，才需要用户在平台编写或确认 schema。

### 5.4 工具目录页面

定位：管理平台内所有可治理、可测试、可授权的具体工具。

应该放：

- 工具列表
- 工具详情
- 新建工具
- 编辑 schema
- 测试调用
- 风险等级
- 可见性
- 版本
- 启用/禁用
- 所属来源
- 调用统计
- 运行审计入口

工具目录里的每一行都应该是一个 `ToolManifest`。

`ToolManifest` 有多种产生路径，但这些路径不是同一种“来源”：

| 产生路径 | 是否自动产生 | 谁提供 schema | 产物归属 |
| --- | --- | --- | --- |
| ToolProvider 同步 | 是，Provider catalog / MCP `tools/list` 同步 | 工具服务提供 | 工具目录 |
| HTTP API 服务连接生成 | 否，用户在工具目录或服务连接详情发起创建 | 平台页面填写或从接口文档生成后确认 | 工具目录 |
| 数据库服务连接生成 | 否，用户选择表/视图/查询模板后生成 | 平台根据查询模板推导并允许确认 | 工具目录 |
| Agent 导出 | 否，用户在 Agent 导出配置中声明 | Agent 导出配置提供 | 工具目录 |
| 手动导入 manifest | 否，用户或管理员导入 | 导入文件提供 | 工具目录 |

因此可以说 ToolProvider 和服务连接都能“产生” `ToolManifest`，但含义不同：ToolProvider 是工具目录同步来源；服务连接是工具生成流程的连接依赖，本身不自动同步工具清单。

推荐创建入口：

| 创建入口 | 用户动作 | 最终后端产物 |
| --- | --- | --- |
| 从工具来源同步 | 来自 AgentPlugin、ToolHost、MCP | `ToolProvider` sync -> `ToolManifest` |
| 新建 HTTP 工具 | 选择 HTTP API 服务连接后，配置一个 HTTP operation | `ToolManifest(executor=http_direct, service_connection_id=...)` |
| 从数据库连接生成 | 选择数据库服务连接、表/视图/查询模板，生成受控查询工具 | 目标态：`ToolManifest(executor=database_query, service_connection_id=...)`；短期可由 ToolHost/MCP 包装 |
| 从 Agent 导出 | 把 Agent 能力包装成工具 | `ToolManifest(executor=agent_tool)` |
| 内置工具 | 平台内置能力 | `ToolManifest` + 内置 executor 或 provider |

这里要特别区分：**HTTP Direct 是工具的 executor，不是独立的一类来源，也不应该作为一个和 HTTP API 工具并列的页面入口**。如果是 HTTP API 场景，通过“选择 HTTP API 服务连接”创建出来的 HTTP 工具，最终也会落成 `executor=http_direct`。目标态只保留“使用服务连接”，删除直接填写 URL 的创建方式。

### 5.5 Agent 详情页的能力配置

Agent 详情页不应该直接绑定“服务连接”或“工具来源”，而应该绑定工具目录里的具体工具。

推荐字段：

- `allowed_tool_ids`
- `denied_tool_ids`
- `allowed_tool_groups`
- 工具版本策略
- 审批策略
- 超时/重试覆盖
- 是否允许外部网络工具

展示上可以按来源分组，但保存时仍然保存具体 `tool_id` 或 group policy。

例子：

```text
客户服务助手
  可用工具
    customer.lookup
    ticket.create
    order.query

这些工具可能来自同一个 ToolHost，也可能是 HTTP API 工具或 Agent 导出工具。
Agent 不需要知道它们背后怎么连，只需要被授权调用哪些 ToolManifest。
```

## 6. 关键工作流

### 6.1 接入 AgentPlugin Service / ToolHost

```text
1. 进入“工具来源”
2. 选择 AgentPlugin Service 或 ToolHost
3. 填写 endpoint、auth_ref、网络范围
4. 平台健康检查
5. 平台同步工具目录
6. 每个 operation 生成 ToolManifest
7. 平台校验 input_schema/output_schema
8. 管理员启用工具
9. 在 Agent 详情页绑定具体 tool_id
```

产物：

- 一个 `ToolProvider`
- 多个 `ToolManifest`
- 可选的调用审计和健康记录

### 6.2 接入 MCP Server

```text
1. 进入“工具来源”
2. 选择 MCP Server
3. 填写 server endpoint / command / auth_ref
4. 平台调用 tools/list
5. 把 MCP tool 转为 ToolManifest
6. 平台执行 schema 校验和 smoke test
7. 启用工具
8. Agent 绑定具体 tool_id
```

注意：MCP 的 `tools/call` 返回可能包含 `content`、`structuredContent`。如果工具目录希望 output schema 直接描述业务对象，需要在 MCP executor 增加输出归一化。

### 6.3 新建 HTTP 工具

HTTP Direct 不是一个 Provider，也不是一类工具来源；它是 HTTP 工具最终落到后端时使用的 executor。用户创建 HTTP 工具时只看到一个入口：“HTTP API 工具”。进入后必须选择或创建 HTTP API 服务连接。

生产 UI 可以只保留“使用服务连接”。这不会减少最终能力，因为平台最终仍然是在调用一个 HTTP operation；它只是把 endpoint、认证、网络范围、健康检查和密钥轮换统一收口到服务连接。

目标态不保留“直接填写完整 URL”。原因是它会把 endpoint、认证、网络边界和健康检查分散到每个工具上，后续治理和代码模型都会变脏。

如果已有历史数据使用了 `executor.url`，应通过一次性迁移处理：

- 为相同 host/base_url 生成 HTTP API 服务连接
- 将工具 executor 改为 `service_connection_id + method/path`
- 迁移后拒绝新的 `executor.url` 写入
- 删除或内部化 `ExecutorSpec.URL`，不再作为公开 API 字段

更合理的表单是：

```text
工具类型：HTTP API 工具
服务连接：选择或新建 HTTP API 服务连接
Operation：method + path + 参数映射 + schema
```

```text
1. 进入“工具目录”
2. 点击“新建工具”
3. 选择工具类型：HTTP API
4. 选择已有 HTTP API 服务连接；如果没有，点击“新建服务连接”进入服务连接创建流程
5. 填写 method、path、headers 映射、timeout、retry
6. 编写 input_schema/output_schema
7. 填写参数映射：input JSON -> request path/query/body/header
8. 执行 smoke test
9. 校验返回结果是否匹配 output_schema
10. 启用工具
11. Agent 绑定 tool_id
```

当前后端 `http_direct` executor 更像直接填写完整 URL。目标态应改成“服务连接 + operation”，不再让工具直接保存完整 URL：

```json
{
  "type": "http_direct",
  "service_connection_id": "conn_customer_api",
  "method": "POST",
  "path": "/tickets/search",
  "request_mapping": {},
  "response_mapping": {}
}
```

这样 endpoint、认证、网络范围由服务连接统一管理，工具只描述 operation。

### 6.4 数据库查询工具

数据库连接不是工具。正确流程是先建连接，再生成受控查询工具。

```text
1. 进入“服务连接”
2. 创建 Database 连接
3. 测试连接
4. 发现 schema/table/view
5. 配置只读范围、表白名单、列白名单、行级过滤
6. 进入“工具目录”
7. 从数据库连接生成查询工具
8. 选择查询模板或安全视图
9. 生成 ToolManifest
10. smoke test + output schema 校验
11. 启用工具
12. Agent 绑定 tool_id
```

短期实现建议：

- 不开放任意 SQL。
- 优先通过 ToolHost/MCP 包装数据库查询。
- 或者只支持预定义查询模板，例如 `query_orders_by_customer_id`。

目标态可以新增 executor：

```text
executor.type = database_query
executor.service_connection_id = conn_orders_db
executor.operation = query_orders_by_customer_id
```

安全默认值：

- 只读
- 参数化查询
- 禁止 DDL/DML
- 表/列白名单
- 最大返回行数
- 超时限制
- 敏感列脱敏
- 全量审计

### 6.5 Agent 导出工具

某个 Agent 可以把自己的能力导出成工具，供其他 Agent 使用。

```text
1. 进入 Agent 详情页
2. 配置“对外导出工具”
3. 填写 tool_id、name、description、input_schema、output_schema
4. 发布后同步为 ToolManifest
5. ToolManifest executor = agent_tool
6. 其他 Agent 在工具目录中选择并绑定该 tool_id
```

这不是服务连接，也不是工具来源接入。它是 Agent 能力工具化。

## 7. API 与数据模型建议

### 7.1 保留现有 CleanCore API

已有 API 边界是合理的：

- `/v1/tool-providers`：工具来源
- `/v1/tool-manifests`：工具目录
- `/v1/agents/{agent_id}/tool-bindings`：Agent 可用工具授权
- `/v1/agents/{agent_id}/exported-tools`：Agent 对外导出工具

### 7.2 明确 ServiceConnection 归属

需要在架构上二选一：

| 方案 | 说明 | 优点 | 风险 |
| --- | --- | --- | --- |
| A. Host/PloyKit 拥有 ServiceConnection | CleanCore 只存 `auth_ref`、endpoint、provider 配置 | 改动小，符合当前 CleanCore 现状 | 前端要调用两个后端，权限/审计要打通 |
| B. CleanCore 原生实现 ServiceConnection | Go 后端新增 store、handler、health、resources | 模型统一，工具来源可直接引用连接 | 实现量更大，需要迁移 OpenAPI 与存储 |

如果目标是让前端“服务连接”页面真实可用，建议选 B 或明确 Host 层代理这些接口。

### 7.3 推荐新增/调整字段

`ToolProvider` 目标态：

```json
{
  "provider_id": "finance_toolhost",
  "provider_type": "static_tool_host",
  "service_connection_id": "conn_finance_toolhost",
  "health": {},
  "sync_policy": {}
}
```

目标态中，`ToolProvider` 不再把 `endpoint` 和 `auth_ref` 作为权威字段；它们应来自 `service_connection_id` 指向的连接资产。迁移期可以保留 `endpoint/auth_ref` 只读兼容字段，但公开创建/更新接口应逐步改为只写 `service_connection_id`。

`ToolManifest` 目标态：

```json
{
  "tool_id": "customer.lookup",
  "input_schema": {},
  "output_schema": {},
  "risk_level": "low",
  "visibility": "tenant",
  "executor": {
    "type": "static_tool_host",
    "provider_id": "customer_toolhost",
    "operation": "customer.lookup"
  }
}
```

HTTP API 工具目标态：

```json
{
  "tool_id": "ticket.search",
  "executor": {
    "type": "http_direct",
    "service_connection_id": "conn_customer_service_api",
    "method": "POST",
    "path": "/tickets/search"
  }
}
```

代码清理目标：

- `http_direct` 的公开创建/更新 payload 不再接受 `executor.url`。
- `ExecutorSpec` 目标态不暴露 `URL` 字段；如果迁移期必须保留，应标记为 legacy/internal。
- `validateManifest` 对 `http_direct` 的校验从“必须有 URL”改为“必须有 `service_connection_id`、`method`、`path`”。
- `HTTPExecutor` 执行时通过 `service_connection_id` 获取 base_url、auth_ref、network_scope，再拼接 method/path。
- OpenAPI 中移除 `http_direct.url` 的公开 schema，改为服务连接引用。
- 现有 `http_direct` URL 测试用例迁移为服务连接引用用例。

数据库查询目标态：

```json
{
  "tool_id": "orders.query_by_customer",
  "executor": {
    "type": "database_query",
    "service_connection_id": "conn_orders_db",
    "operation": "query_by_customer"
  }
}
```

## 8. Schema 对齐与校验

工具 schema 对齐应该分四段做，而不是只相信企业服务声明。

### 8.1 注册时校验

ToolManifest 必须包含：

- `tool_id`
- `name`
- `description`
- `input_schema`
- `output_schema`
- `executor.type`
- 对应 executor 的必要字段

当前后端已有基础校验：缺少 `input_schema` 或 executor 字段会拒绝。需要注意的是，当前 Go 代码没有强制 `output_schema` 非空，且空 schema 会跳过输出校验；这是目标态需要补上的治理约束。建议规则是：工具可以保存为 `draft` 时缺少 `output_schema`，但进入 `validated/enabled` 前必须补齐。

### 8.2 同步后校验

从 ToolHost/MCP 同步后的工具进入 `synced` 状态，不能直接等于可用。

需要执行：

- JSON Schema 结构合法性校验
- 必填字段检查
- schema 示例生成或示例回放
- smoke test
- 输出结构与 `output_schema` 校验

通过后进入 `validated`，再由管理员启用为 `enabled`。

### 8.3 调用前校验

Agent 调用工具前，运行时必须校验：

- 工具存在
- 工具启用
- Provider 健康
- Agent tool bindings 允许
- 风险策略允许
- 审批策略已满足
- 输入参数匹配 `input_schema`

当前 `ToolRuntime` 已经有 input schema 校验。

### 8.4 调用后校验

工具返回后，运行时必须校验输出是否匹配 `output_schema`。

当前 `ToolRuntime` 已经有 output schema 校验。若失败，应把调用标记为 failed，并记录：

- tool_id
- provider_id
- executor_type
- schema_validation_error
- request_id / trace_id

## 9. 权限与治理边界

### 9.1 全局可见不等于全局可用

工具目录可以是租户全局目录，但这不代表所有 Agent 都能调用。

推荐权限链路：

```text
Tenant 可见
  -> Workspace 可见
  -> ToolManifest enabled
  -> Provider enabled + healthy
  -> Agent tool_bindings allowed
  -> Runtime policy allowed
  -> Human approval if required
```

### 9.2 Agent 不绑定服务连接

Agent 绑定服务连接会造成权限过粗。例如绑定一个客户系统 API 连接后，Agent 是否能调用所有 endpoint 不清楚。

正确做法是：

- 服务连接定义“怎么连”
- 工具定义“能做什么 operation”
- Agent 绑定“允许使用哪些 operation”

### 9.3 HTTP API 工具风险

HTTP API 工具底层使用 `http_direct` executor。目标态只允许它引用 HTTP API 服务连接，不保留原始 URL 配置。

HTTP API 工具仍然需要治理：

- 必须引用已启用、健康的 HTTP API 服务连接
- 必须有明确 input/output schema
- 必须 smoke test 成功
- 必须配置超时、重试和最大响应大小
- 高风险操作需要审批策略
- 调用必须进入追踪与审计

原始 URL 配置不作为目标能力保留。历史数据可以迁移读取，但迁移完成后应拒绝新的原始 URL 写入。

当前后端治理代码里已经能识别 `http_direct` executor，并存在禁用 HTTP Direct 的治理判断。目标态建议把治理粒度细化为：

- 拒绝没有 `service_connection_id` 的 HTTP API 工具
- 允许引用健康服务连接的 HTTP API 工具

## 10. 状态机建议

### 10.1 服务连接状态

```text
draft -> tested -> healthy -> enabled
                -> unhealthy
enabled -> disabled
```

### 10.2 工具来源状态

当前代码层 `ToolProvider.Status` 只支持 `draft/enabled/disabled`，`health_status` 单独记录健康。下面是产品目标态，可通过状态字段扩展，或通过 `status + health_status + sync_result` 组合表达。

```text
draft -> healthy -> catalog_synced -> validated -> enabled
                         |              |
                         v              v
                      sync_failed     validation_failed
enabled -> disabled
```

### 10.3 工具状态

当前代码层 `ToolManifest.Status` 只支持 `draft/enabled/disabled`。下面是产品目标态，可通过新增状态值实现，也可以先用治理视图中的校验结果表达。

```text
draft -> synced/imported -> validated -> enabled
                              |
                              v
                         validation_failed
enabled -> disabled -> deprecated
```

### 10.4 Agent 绑定状态

Agent 工具绑定应跟随 Agent 草稿/版本发布：

```text
draft binding -> release review -> active version binding
```

不要因为一个工具存在于目录，就自动进入所有 Agent 的 active binding。

## 13. 实施阶段

### Phase 1：前端概念整理，不大改后端

- 菜单改名：工具 -> 工具目录，企业工具服务 -> 工具来源。
- 服务连接页只展示连接资产。
- HTTP API 工具入口放在工具目录，但在 ServiceConnection 后端未补齐前不作为生产可用入口开放；避免为了先上线又恢复“直接填写 URL”。
- Agent 创建页只选择具体工具，不选择工具来源/服务连接。
- 文案明确：Agent 可不带技能和工具创建。

### Phase 2：后端补齐 ServiceConnection

- 明确 ServiceConnection 归属。
- 如果归属 CleanCore，新增 Go handler/store/health/resources。
- `ToolProvider` 支持 `service_connection_id`，并逐步把 `endpoint/auth_ref` 降级为迁移期兼容字段。
- `ExecutorSpec` 新增 `service_connection_id`、`path`、request/response mapping；`http_direct` 改为必须引用 HTTP API 服务连接。
- `parseToolExecutorSpec`、`validateManifest`、`HTTPExecutor`、OpenAPI、测试用例同步从 `url` 模型迁到 `service_connection_id + method/path` 模型。
- 增加一次性迁移：按旧 `executor.url` 的 host/base_url 创建 HTTP API 服务连接，再回填工具的 `service_connection_id + path`。
- 迁移完成后删除原始 URL 公开写入能力。
- 工具目录展示 connection/provider 引用关系。

## 15. 最终推荐口径

推荐对产品和前端统一使用下面这套话术：

- **服务连接**：我怎么连到一个外部系统。
- **工具来源**：我从哪里同步一批工具，并由谁执行这些工具。
- **工具目录**：平台里有哪些具体可调用工具。
- **Agent 工具绑定**：这个 Agent 被允许调用哪些具体工具。

对应用户路径：

```text
需要复用外部 endpoint/认证时，先建服务连接
  -> 再接入工具来源或新建工具
  -> 工具进入工具目录
  -> 管理员治理和测试
  -> Agent 绑定具体工具
  -> 运行时按 schema、权限、审批、审计执行
```

这能解决“先有鸡还是先有蛋”的问题：Agent 可以先创建为空壳；工具也可以先进入目录；两者通过后续绑定关联，不要求创建时互相依赖。
