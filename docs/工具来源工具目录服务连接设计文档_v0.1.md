# 工具来源、工具目录与服务连接设计文档 v0.1

## 0. 本轮审计结论

结合当前 Go 代码和 OpenAPI 后，本文档需要坚持五个硬边界：

- CleanCore 当前已真实实现 `ServiceConnection`、`ToolProvider`、`ToolManifest`、`ToolRuntime`、Agent `tool_bindings`、Agent `exported-tools`；服务连接已经进入 Go 主干和 clean-core OpenAPI。
- 公开 `http_direct` 已从 Go runtime、OpenAPI 和 e2e 可执行路径中删除；旧 executor 只作为负向测试用例保留。HTTP API 工具后续只能由平台内置 Adapter Provider 包装服务连接，再通过 `provider_id + operation` 生成。
- 目标态删除原始 URL 创建能力，不做“服务连接模式/直接 URL 模式”两套长期分支。开发期数据、测试和脚本直接改向新模型。
- 开发阶段不为了兼容旧 payload 牺牲模型干净度。`ToolProvider.endpoint/auth_ref`、`executor.url/method/headers`、`secret_ref/token_ref` 这类旧字段，以及 `{"connection": {...}}`、`{"provider": {...}}`、`{"manifest": {...}}`、`{"tool": {...}}`、`{"operation": {...}}`、`{"group": {...}}` 这类资源壳请求体，只允许作为拒绝用例或历史说明存在，不作为兼容输入继续保留。
- `ToolProvider` 和 `ServiceConnection` 都可能参与生成 `ToolManifest`，但层级不同：`ToolProvider` 是工具注册/同步主体，`ServiceConnection` 是连接资产。服务连接不直接生成 `ToolManifest`，而是经由外部或平台内置的 ToolProvider 生成。

本轮重构后的推荐模型：

```text
ServiceConnection
  只管连接资产：base_url / auth_type / auth_ref / network_scope / health / resources
        |
        | 被 ToolProvider 引用
        v
ToolProvider
  外部工具来源：AgentPlugin Service / ToolHost / MCP Server
  平台内置连接适配器：HTTP API Adapter / Database Query Adapter
        |
        | sync / generate
        v
ToolManifest

ToolManifest
  是 Agent 最终绑定和运行时调用的唯一工具单元
```

## 1. 背景

当前前端同时出现了“工具”“企业工具服务”“服务连接”“AgentPlugin Service 接入”“ToolHost”“HTTP Direct”等概念，用户会自然产生几个疑问：

- 工具到底是企业提供的能力，还是智能体自己的能力？
- 服务连接和企业工具服务是不是同一个东西？
- HTTP Direct 应该放在服务连接里，还是工具来源里？
- Agent 创建时到底应该绑定工具服务、工具目录，还是具体工具？

这份文档给出一个统一边界：**服务连接管连接，工具来源管同步/执行工具目录，工具目录管可调用能力，Agent 只绑定具体工具权限**。

## 2. 结论摘要

| 概念 | 一句话定义 | 创建后产生什么 | 是否直接给 Agent 使用 |
| --- | --- | --- | --- |
| 服务连接 | 外部系统的 endpoint、认证、网络、健康检查、资源发现配置 | `ServiceConnection` | 否 |
| 工具来源 | 能暴露工具清单并执行工具调用的 Provider | `ToolProvider`，同步出多个 `ToolManifest` | 否 |
| 工具目录 | 平台内被治理、可测试、可授权的具体工具清单 | `ToolManifest` | 是，Agent 绑定 `tool_id` |
| Agent 工具绑定 | 某个 Agent 能用哪些工具的授权配置 | `tool_bindings` | 是 |
| Agent 对外导出工具 | 把某个 Agent 的能力包装成工具 | `ToolManifest(executor=agent_tool)` | 可被其他 Agent 绑定 |

关键口径：

- **服务连接不是工具**。它只是连接资产，例如 HTTP API、数据库、Webhook、Origin API、OAuth、缓存、队列、存储。
- **工具来源不是单个工具**。它是能够同步工具目录并执行工具调用的服务，例如 ToolHost、AgentPlugin Service、MCP Server。
- **工具目录里的 ToolManifest 才是 Agent 可绑定的东西**。
- **HTTP Direct 不是工具来源**。它是旧模型里的 executor，当前不作为公开工具创建入口。HTTP API 工具通过服务连接和平台内置 Adapter Provider 进入工具目录。
- **数据库查询能力不是服务连接本身**。数据库服务连接只证明能连上库；真正给 Agent 用的应是由连接生成/注册出来的查询工具。

## 3. 当前后端代码对齐

当前 Go 后端里，“工具来源”“工具目录”和“服务连接”已经有比较明确的主干模型。服务连接负责连接资产，ToolProvider 通过 `service_connection_id` 引用连接并同步/执行工具。

### 3.1 已落地

| 后端对象 | 代码位置 | 含义 |
| --- | --- | --- |
| `ServiceConnection` | `internal/serviceconnection/service.go` | 服务连接资产，管理 `base_url/auth_ref/network/health/resources` |
| `ToolProvider` | `internal/tool/catalog/catalog.go` | 工具来源/Provider，当前支持 `static_tool_host`、`agent_plugin_service`、`mcp`、`http_api_adapter`、`database_adapter` |
| `ToolManifest` | `internal/tool/catalog/catalog.go` | 工具目录里的具体工具，包含 `tool_id`、schema、risk、visibility、executor |
| `ExecutorSpec` | `internal/tool/catalog/catalog.go` | schema 可表达 `static_tool_host`、`agent_plugin_service`、`mcp`、`agent_tool`、`http_api_adapter`、`database_adapter`；两类 managed adapter executor 都由 AdapterOperation 内部发布生成，公开 manifest upsert 不接受手工创建 |
| `ToolRuntime` | `internal/tool/runtime/runtime.go` | 工具运行时，调用前校验 input schema，调用后校验 output schema |
| Agent `tool_bindings` | `internal/server/handlers_agent_tool_bindings.go` | Agent 可用工具授权，不负责创建工具 |
| Agent `exported-tools` | `internal/server/handlers_agent_exported_tools.go` | 把 Agent 能力同步为工具目录里的 `agent_tool` |

### 3.2 产品契约已按核心边界收敛

CleanCore 的 `docs/openapi.clean-core.v1.json` 已补齐 `/v1/service-connections`。产品 `docs/openapi.yaml` 已按核心边界收敛服务连接、ToolProvider、AdapterOperation 和 ToolManifest 关键契约。后续页面级聚合接口可以由 BFF/前端组合基础接口生成，不应为了页面方便把 `toolhost` 放进服务连接类型，也不应恢复 HTTP Direct 双入口。

服务连接推荐类型是：

- `clean_core`
- `http_api`
- `database`
- `webhook`
- `oauth`
- `cache`
- `queue`
- `storage`

其中 `toolhost`、`agent_plugin_service`、`mcp` 应归工具来源/ToolProvider，不归服务连接类型。

### 3.3 关键缺口

- HTTP API Adapter Provider / AdapterOperation 已进入 CleanCore 主干，支持基于 `service_connection_id + method + path + schema` 发布 `ToolManifest`，也支持通过 `from-resource` 从服务连接已发现的 `http_operation` 生成 AdapterOperation 草稿；请求映射覆盖 `path_params/query/headers/body`，响应映射覆盖 `body_path/output`，并拒绝混入数据库专属字段。
- 数据库工具 Adapter 已有 Provider/Operation/Manifest 字段建模；Postgres 服务连接已支持 table/view 资源发现；只读 SQL 执行器已进入主链路，可通过 AdapterOperation publish/sync 暴露为 ToolManifest，并支持通过 `from-resource` 从已发现 table/view 生成查询草稿、默认 output_schema 和可编辑 query_template，同时支持基于已发现 `resource_id` 的资源绑定、`redact_columns` 列存在性校验和基础结果列脱敏，并拒绝混入 HTTP request/mapping 字段。
- 非 Postgres 数据库、缓存、队列、存储类服务连接还没有真实连接测试和资源发现，当前只完成建模和存储；cache/queue/storage 的连接 test 明确返回 unknown + not implemented，不能假装 healthy。
- MCP 输出已归一化：若 `tools/call` 返回 `structuredContent`，运行时直接把它作为业务输出；没有结构化内容时才返回 `{content: ...}` 包装。

## 4. 领域模型

推荐模型如下：

```text
ServiceConnection
  管 endpoint / auth_type / auth_ref / network / health / resources
  例如 HTTP API、Database、Webhook、Origin API
        |
        | 被 ToolProvider 引用，复用连接、认证、网络边界
        v
ToolSource / ToolProvider
  外部 Provider：AgentPlugin Service、ToolHost、MCP Server
  托管 Provider：HTTP API Adapter、Database Adapter
        |
        | sync catalog / generate operation
        v
ToolCatalog / ToolManifest
  管具体工具的 schema、risk、visibility、executor、版本、测试
  例如 customer.lookup、ticket.create、db.query_orders
        |
        | allow / deny / bind tool_id
        v
Agent tool_bindings
  管某个 Agent 能用哪些工具
        |
        v
ToolRuntime
  校验输入 -> 执行工具 -> 校验输出 -> 审计追踪
```

### 4.1 工具来源和服务连接不是两个工具来源

服务连接不是第二个工具来源。它和工具来源是上下游/依赖关系：

- **服务连接**解决“怎么连到一个外部系统”，例如 base_url、认证、网络范围、健康检查。
- **工具来源**解决“从哪里同步一批工具，以及这些工具由谁执行”，例如 ToolHost、AgentPlugin Service、MCP Server。
- **工具目录**解决“平台里最终有哪些可授权调用的具体工具”。

更干净的终态是：所有可调用工具都通过某种 `ToolProvider` 注册到工具目录。服务连接不直接注册工具，它只被 ToolProvider 或工具生成流程引用。

企业工具服务可以分成两类：

| 类型 | 谁实现 | 连接来源 | 如何产生 ToolManifest |
| --- | --- | --- | --- |
| 外部工具来源 | 企业或第三方实现 AgentPlugin Service / ToolHost / MCP Server | 可引用 HTTP API 服务连接，或由 provider 自带连接配置 | provider catalog / MCP `tools/list` 同步 |
| 平台内置连接适配器 | 平台实现“HTTP API Adapter / Database Adapter”这类托管 Provider | 必须引用服务连接 | HTTP API 和 Database Adapter 均可通过 operation publish/sync 生成 ToolManifest |

这意味着“服务连接中的接口连接只能通过其他方式的 ToolHost 接入 Agent 工具注册”是一个合理且更干净的设计。这里的“其他方式的 ToolHost”建议命名为**平台内置连接适配器**或**托管 ToolProvider**，避免和企业外部 ToolHost 混淆。

工具来源可以引用服务连接，但服务连接不会因此变成工具来源。例子：

```text
HTTP API 服务连接
  -> 被 HTTP API 工具引用
  -> 生成 ToolManifest

HTTP API 服务连接
  -> 被 ToolProvider 引用
  -> ToolProvider 同步工具清单
  -> 生成多个 ToolManifest
```

因此，“工具来源中的工具”不会出现在服务连接中作为工具清单管理。它们只应该出现在工具目录中。服务连接详情页最多展示只读的“被引用对象”，例如被哪个 ToolProvider 引用、被哪些 HTTP API 工具引用，方便追踪影响范围。

注意：即使 ToolProvider 需要复用连接资产，服务连接也应保持通用连接语义，例如 `http_api`、`oauth`、`database`。不要把 `toolhost` 做成服务连接里的业务类型；ToolHost、AgentPlugin、MCP 这些语义应由 `ToolProvider.provider_type` 或工具来源页面表达。

更准确的说法是：服务连接管理和创建的是**接口型连接资产**，这些连接资产可以被“工具化”。例如 HTTP API 服务连接本身不是工具，但可以基于它创建一个或多个 HTTP API 工具：

```text
HTTP API 服务连接
  -> customer.lookup
  -> ticket.create
  -> order.refund
```

从 Agent 视角看，Agent 不关心这些工具背后来自 ToolHost、MCP、Agent 导出，还是 HTTP API Adapter。Agent 只看到工具目录里的 `ToolManifest`，并通过 `tool_id` 获得授权。

所以“服务连接是不是工具提供者”要分两层回答：

- 业务语义上：可以说它是某些工具能力的上游连接来源。
- 产品/代码模型上：不要把它定义成 `ToolProvider` 或工具来源；它只是被 `ToolManifest` 或 `ToolProvider` 引用的连接资产。

### 4.2 为什么要分层

如果不分层，会出现两个问题：

- 一个 HTTP API 既像服务连接，又像工具，又像工具来源，页面和接口都会重复。
- Agent 绑定“企业工具服务”太粗，会导致一个服务里的所有工具是否都能被 Agent 使用变得不清楚。

分层后，每个问题都有唯一归属：

- 连接是否可用：看服务连接。
- 一个 Provider 是否能同步工具清单：看工具来源。
- 一个具体 operation 能不能被调用：看工具目录的 ToolManifest。
- 某个 Agent 是否能调用它：看 Agent 的 tool bindings。

## 5. 页面设计

### 5.1 左侧导航建议

建议把当前“构建/连接/运行”保留，但调整命名和职责：

```text
构建
  智能体
  技能
  工具目录

连接
  工具来源
  服务连接

运行
  运行记录
  待审批
  追踪与审计
```

命名建议：

- 当前“工具”建议改成 **工具目录**。
- 当前“企业工具服务”建议改成 **工具来源**。
- 当前“服务连接”保留，但只放连接资产，不放 ToolHost/AgentPlugin/MCP 的接入编排。

### 5.2 服务连接页面

定位：统一管理外部系统连接，不直接创建 Agent 可调用工具。

应该放：

- HTTP API 连接
- 数据库连接
- Webhook 连接
- Origin API / CleanCore 连接
- OAuth / Secret 引用
- 缓存、队列、存储连接

主要能力：

- 新建连接
- 测试连接
- 健康检查
- 认证引用/密钥轮换
- 网络访问范围
- 权限范围
- 资源发现，例如数据库表、API base path、Webhook topic
- 启用/禁用
- 审计

不应该放：

- AgentPlugin Service 接入向导
- ToolHost 工具目录同步
- MCP tools/list 同步
- 完整的 HTTP API 工具创建表单
- Agent 工具绑定

服务连接页面的结果是：

```text
connection_id
connection_type
endpoint/base_url
auth_type
auth_ref
network_scope
health_status
resource_index
```

`auth_type` 是连接认证类型枚举：`none`、`api_key`、`bearer`、`basic`、`oauth2`、`signed_request`、`mtls`。无认证连接统一保存为 `auth_type=none` 且 `auth_ref` 为空；只要填写 `auth_ref` 就必须选择非 `none` 的 `auth_type`。`auth_ref` 只是凭据引用，不能提交真实密钥，也不再接受 `secret_ref/token_ref` 兼容别名。密钥轮换同样要求提交显式 `auth_type + auth_ref`，平台只记录 ref hash 和 auth_type。

`network_scope` 是连接级 host allowlist，可填写逗号/空白分隔的 host 或 JSON 字符串数组。HTTP 类连接显式配置 `network_scope` 时必须包含 `base_url` host，可额外包含其它 host 或通配域名。ToolHost/MCP/HTTP API Adapter 生成工具时会把它下发到 HTTP execution profile 的 `network_policy.allowed_hosts`；未配置时默认只允许 `base_url` host，避免工具获得任意网络访问。

`health_status`、`last_health_at`、`last_health_error` 和 `resource_index` 是运行观测或资源发现结果，不是用户创建/更新连接时提交的配置。CleanCore domain 普通 `Upsert` 也不保存调用方传入的健康观测字段；只有连接 test 能写健康观测。数据库连接的 endpoint/auth/driver 等身份字段变化时，已发现资源目录应清空，避免旧库表 schema 被新连接继续复用。

服务连接可以被 ToolProvider 或平台内置 Adapter operation 引用，也可以作为创建 HTTP API 工具的起点，但它本身不是工具，不能直接绑定给 Agent，也不直接同步工具清单。

HTTP API 工具可以“从服务连接发起创建”，但不能“归属于服务连接管理”。也就是说，服务连接详情页可以有一个快捷动作：

```text
服务连接详情 -> 创建 HTTP API 工具
```

这个动作只是打开工具目录的新建工具流程，并预填当前 `service_connection_id`。保存后应创建或更新 HTTP API Adapter operation，再由 Adapter Provider 生成工具目录里的 `ToolManifest`。工具 schema、启用状态、测试、授权和审计仍由工具目录管理。

HTTP API 服务连接的主创建入口在这里：

```text
左侧导航：连接 -> 服务连接 -> 新建服务连接 -> 类型选择 HTTP API
```

工具目录的新建 HTTP API 工具页可以提供“新建服务连接”快捷入口，但它应该是跳转、弹窗或抽屉式创建服务连接，创建成功后回填 `service_connection_id` 到 Adapter operation 配置。连接定义仍归服务连接页面管理，不归工具表单管理。

### 5.3 工具来源页面

定位：管理“能提供一批工具”的 Provider。

应该放：

- AgentPlugin Service 接入
- ToolHost 接入
- MCP Server 接入
- 工具目录同步
- Provider 健康检查
- Provider 级别启用/禁用
- Provider 级别权限、风险、调用策略

不应该放：

- HTTP API 工具创建
- 数据库连接本身
- 普通 REST API 连接本身
- 单个工具的 schema 编辑
- Agent 绑定工具

推荐来源类型：

| 来源类型 | 后端映射 | 说明 |
| --- | --- | --- |
| AgentPlugin Service | `ToolProvider(provider_type=agent_plugin_service)` | 企业按平台协议实现的工具服务，可通过 well-known/catalog 同步，执行协议复用 ToolHost catalog/invoke |
| ToolHost | `ToolProvider(provider_type=static_tool_host)` | 标准工具宿主，负责目录同步和执行 |
| MCP Server | `ToolProvider(provider_type=mcp)` | 通过 MCP `tools/list` 同步，通过 `tools/call` 执行 |

ToolHost 不应该移动到服务连接中。当前模型里 ToolHost 可以引用一个 HTTP API 服务连接来复用 endpoint/auth/network，但产生工具清单的仍然是 ToolProvider：

```text
HTTP API 服务连接
  -> ToolProvider(provider_type=static_tool_host, service_connection_id=...)
  -> SyncProviderCatalog
  -> 多个 ToolManifest
```

不是：

```text
HTTP API 服务连接
  -> 多个 ToolManifest
```

ToolHost 和服务连接的粒度建议：

- **一个 ToolHost 是一个工具服务/Provider，不是一条普通服务连接**。当前 CleanCore 代码里，一个 `ToolProvider` 通过 `service_connection_id` 引用连接资产；同步时从连接解析出的地址拉取多个 catalog item，每个 item 变成一个 `ToolManifest`。
- **ToolHost 里的一个 API/operation 不是服务连接**。它是工具目录里的一个具体工具，表现为 `ToolManifest.executor.provider_id + operation`。
- **ToolHost 可以由多个下游连接组成**。比如财务 ToolHost 内部可能访问数据库、缓存、ERP HTTP API，但这些是 ToolHost 自己的实现依赖；当前 CleanCore 不建模这些内部连接。
- **数据库、缓存、存储可以被工具化，但不建议“放进 ToolHost 页面当连接创建”**。更清晰的做法是：数据库/缓存/存储仍在服务连接中管理；如果要给 Agent 用，数据库当前由平台内置 Database Adapter Provider 生成 `ToolManifest`，复杂写操作或跨系统编排交给外部 ToolHost/MCP；Cache/Storage Adapter 后续再补。

工具来源创建成功后，不代表 Agent 已经能使用这些工具。它只代表平台发现了一批候选工具，后续还要进入工具目录治理，再由 Agent 绑定具体 `tool_id`。

Schema 处理原则：

- 接入 ToolHost、AgentPlugin Service、MCP Server 时，不应要求用户在平台页面手写每个工具的 schema。
- 工具服务必须在 catalog / `tools/list` 中声明 `input_schema` 和 `output_schema`，平台负责同步、校验、预览和治理。
- 接入页可以允许管理员修正描述、风险等级、可见性、标签、审批策略，但不建议在这里编辑真实 schema。
- 如果同步来的 schema 不合法或缺失，工具应停留在 `validation_failed` 或 `draft` 状态，提示回工具服务修复。
- 只有 HTTP API 工具、手动导入 manifest、Agent 导出、数据库查询模板生成这类“平台内创建具体工具”的场景，才需要用户在平台编写或确认 schema。

### 5.4 工具目录页面

定位：管理平台内所有可治理、可测试、可授权的具体工具。

应该放：

- 工具列表
- 工具详情
- 新建工具
- 编辑 schema
- 测试调用
- 风险等级
- 可见性
- 版本
- 启用/禁用
- 所属来源
- 调用统计
- 运行审计入口

工具目录里的每一行都应该是一个 `ToolManifest`。

`ToolManifest` 有多种产生路径，但这些路径不是同一种“来源”：

| 产生路径 | 是否自动产生 | 谁提供 schema | 产物归属 |
| --- | --- | --- | --- |
| ToolProvider 同步 | 是，Provider catalog / MCP `tools/list` 同步 | 工具服务提供 | 工具目录 |
| 平台内置 HTTP API Adapter 生成 | 否，用户选择 HTTP API 服务连接并配置 operation | 平台页面填写或从接口文档生成后确认 | 工具目录 |
| 平台内置 Database Adapter 生成 | 否，用户选择数据库连接、表/视图/查询模板后生成 | 平台根据查询模板推导并允许确认 | 工具目录 |
| Agent 导出 | 否，用户在 Agent 导出配置中声明 | Agent 导出配置提供 | 工具目录 |
| 手动导入 manifest | 否，用户或管理员导入 | 导入文件提供 | 工具目录 |

因此更准确地说：`ToolManifest` 总是由某类工具注册主体产生。外部工具来源通过 ToolProvider 同步；HTTP API 和数据库这类服务连接通过平台内置 Adapter 生成。服务连接本身不自动同步工具清单。

推荐创建入口：

| 创建入口 | 用户动作 | 最终后端产物 |
| --- | --- | --- |
| 从工具来源同步 | 来自 AgentPlugin、ToolHost、MCP | `ToolProvider` sync -> `ToolManifest` |
| 新建 HTTP 工具 | 选择 HTTP API 服务连接后，配置一个 HTTP operation | HTTP API Adapter operation -> `ToolManifest(executor=provider_id+operation)` |
| 从数据库连接生成 | 选择数据库服务连接、表/视图/查询模板，生成受控查询工具 | Database Adapter operation -> `ToolManifest(executor=provider_id+operation)`；运行时执行只读 SQL，复杂写操作仍交给 ToolHost/MCP |
| 从 Agent 导出 | 把 Agent 能力包装成工具 | `ToolManifest(executor=agent_tool)` |
| 内置工具 | 平台内置能力 | `ToolManifest` + 内置 executor 或 provider |

这里要特别区分：**HTTP Direct 是旧模型里的 executor，不是独立的一类来源，也不应该作为一个和 HTTP API 工具并列的页面入口**。如果是 HTTP API 场景，应通过平台内置 HTTP API Adapter Provider 生成工具；开发阶段直接删除公开 `http_direct` 能力。

### 5.5 Agent 详情页的能力配置

Agent 详情页不应该直接绑定“服务连接”或“工具来源”，而应该绑定工具目录里的具体工具。

推荐字段：

- `allowed_tool_ids`
- `denied_tool_ids`
- `allowed_tool_groups`
- 工具版本策略
- 审批策略
- 超时/重试覆盖
- 是否允许外部网络工具

展示上可以按来源分组，但保存时仍然保存具体 `tool_id` 或 group policy。

例子：

```text
客户服务助手
  可用工具
    customer.lookup
    ticket.create
    order.query

这些工具可能来自同一个 ToolHost，也可能是 HTTP API 工具或 Agent 导出工具。
Agent 不需要知道它们背后怎么连，只需要被授权调用哪些 ToolManifest。
```

## 6. 关键工作流

### 6.1 接入 AgentPlugin Service / ToolHost

```text
1. 进入“工具来源”
2. 选择 AgentPlugin Service 或 ToolHost
3. 选择或创建一个 HTTP API 服务连接，由连接管理 endpoint、auth_type/auth_ref、网络范围
4. 平台基于服务连接做健康检查
5. 平台同步工具目录
6. 每个 operation 生成 ToolManifest
7. 平台校验 input_schema/output_schema
8. 管理员启用工具
9. 在 Agent 详情页绑定具体 tool_id
```

产物：

- 一个 `ToolProvider`
- 多个 `ToolManifest`
- 可选的调用审计和健康记录

### 6.2 接入 MCP Server

```text
1. 进入“工具来源”
2. 选择 MCP Server
3. 远程 MCP 选择或创建服务连接；本地 command 型 MCP 填写 command 特定参数
4. 平台调用 tools/list
5. 把 MCP tool 转为 ToolManifest
6. 平台执行 schema 校验和 smoke test
7. 启用工具
8. Agent 绑定具体 tool_id
```

注意：MCP 的 `tools/call` 返回可能包含 `content`、`structuredContent`。当前执行器优先返回 `structuredContent` 作为业务对象，因此工具目录里的 `output_schema` 默认描述业务对象；只有缺少 `structuredContent` 时，才返回 `{content: ...}` 包装对象。

### 6.3 新建 HTTP 工具

HTTP Direct 不是一个 Provider，也不是一类工具来源；它是旧模型里的历史 executor。用户创建 HTTP 工具时只看到一个入口：“HTTP API 工具”。进入后必须选择或创建 HTTP API 服务连接，并由平台内置 HTTP API Adapter Provider 负责执行这些 operation。

生产 UI 可以只保留“使用服务连接”。这不会减少最终能力，因为平台最终仍然是在调用一个 HTTP operation；它只是把 endpoint、认证、网络范围、健康检查和密钥轮换统一收口到服务连接。

不保留“直接填写完整 URL”。原因是它会把 endpoint、认证、网络边界和健康检查分散到每个工具上，后续治理和代码模型都会变脏。

开发阶段不为已有 `executor.url` 做长期迁移兼容。测试数据、seed 数据和脚本应直接重写为 HTTP API Adapter Provider + operation。代码中删除或内部化 `ExecutorSpec.URL`，不再作为公开 API 字段。

更合理的表单是：

```text
工具类型：HTTP API 工具
服务连接：选择或新建 HTTP API 服务连接
Operation：method + path + 参数映射 + schema
```

```text
1. 进入“工具目录”
2. 点击“新建工具”
3. 选择工具类型：HTTP API
4. 选择已有 HTTP API 服务连接；如果没有，点击“新建服务连接”进入服务连接创建流程
5. 填写 method、path、headers 映射、timeout、retry
6. 编写 input_schema/output_schema
7. 填写参数映射：input JSON -> request path/query/body/header
8. 执行 smoke test
9. 校验返回结果是否匹配 output_schema
10. 启用工具
11. Agent 绑定 tool_id
```

旧后端 `http_direct` executor 更像直接填写完整 URL。当前应统一改成“服务连接 + Adapter Provider + operation”，不再让工具直接保存完整 URL：

```json
{
  "provider_id": "managed_http_api_adapter",
  "provider_type": "http_api_adapter",
  "operation": {
    "operation_id": "ticket.search",
    "service_connection_id": "conn_customer_api",
    "method": "POST",
    "path": "/tickets/search"
  }
}
```

`managed_http_api_adapter` 是 CleanCore 固定内置 Provider，不通过“工具来源”页面创建。这样 endpoint、认证、网络范围由服务连接统一管理，内置 Provider 负责执行 operation，ToolManifest 只通过 `provider_id + operation` 指向具体工具能力。

### 6.4 数据库查询工具

数据库连接不是工具。正确流程是先建连接，再生成受控查询工具。

```text
1. 进入“服务连接”
2. 创建 Database 连接
3. 测试连接
4. 发现 schema/table/view
5. 配置只读范围、表白名单、列白名单、行级过滤
6. 进入“工具目录”
7. 从数据库连接生成查询工具
8. 选择查询模板或安全视图
9. 保存 Database Adapter operation
10. 配置 output schema、最大行数、`redact_columns` 和审计策略
11. 后端校验 `resource_id` 必须命中该连接已发现 table/view，`redact_columns` 必须命中已发现列
12. 只允许只读 SQL；公开 manifest upsert 不接受手工 `executor.type=database_adapter`
13. publish 后 Agent 绑定 tool_id
```

当前实现边界：

- 不开放任意 SQL。
- 只允许只读查询模板。
- 启用、test、publish 和运行时安装都会校验 `resource_id` 命中已发现 table/view，并要求 `query_template` 的 `FROM/JOIN` 关系显式命中绑定资源。
- `redact_columns` 必须命中已发现列。
- 复杂写操作或跨系统编排通过 ToolHost/MCP 包装。

Database Adapter Provider 已进入主干：

```json
{
  "provider_id": "managed_database_adapter",
  "provider_type": "database_adapter",
  "operation": {
    "operation_id": "orders.query_by_customer",
    "service_connection_id": "conn_orders_db",
    "resource_id": "public.orders",
    "query_template": "select id, total, customer_email from public.orders where customer_id = :customer_id",
    "parameter_schema": {
      "type": "object"
    },
    "max_rows": 100,
    "redact_columns": ["customer_email"]
  }
}
```

`managed_database_adapter` 同样是固定内置 Provider。产品页不需要让用户先创建一个数据库 Adapter Provider；用户创建的是数据库连接和查询 operation。

安全默认值：

- 只读
- 参数化查询
- 禁止 DDL/DML
- 表/列白名单：当前用服务连接已发现资源目录约束 `resource_id`，并校验 `redact_columns` 必须是已发现列
- 最大返回行数
- 超时限制
- 敏感列脱敏：当前用 AdapterOperation 的 `redact_columns` 做基础列级遮蔽，并在启用、test、publish 和运行时安装前校验列来自已发现资源；更复杂的按角色/策略脱敏后续扩展。
- 生命周期审计：AdapterOperation 的 upsert/test/publish 已写入 audit，运行时调用继续通过 trace 记录 provider_id、operation_id、connection_id。

### 6.5 Agent 导出工具

某个 Agent 可以把自己的能力导出成工具，供其他 Agent 使用。

```text
1. 进入 Agent 详情页
2. 配置“对外导出工具”
3. 填写 tool_id、name、description、input_schema、output_schema
4. 发布后同步为 ToolManifest
5. ToolManifest executor = agent_tool
6. 其他 Agent 在工具目录中选择并绑定该 tool_id
```

这不是服务连接，也不是工具来源接入。它是 Agent 能力工具化。

## 7. API 与数据模型建议

### 7.1 保留现有 CleanCore API

已有 API 边界是合理的：

- `/v1/tool-providers`：工具来源
- `/v1/tool-manifests`：工具目录
- `/v1/agents/{agent_id}/tool-bindings`：Agent 可用工具授权
- `/v1/agents/{agent_id}/exported-tools`：Agent 对外导出工具

`GET /v1/tool-providers` 默认服务于“工具来源”页面，只返回外部工具来源：AgentPlugin Service、ToolHost、MCP Server。HTTP API Adapter 和 Database Adapter 是平台内置 Provider，默认不混入工具来源列表；治理、影响分析或排障视图需要看全量 Provider 事实时，显式使用 `include_managed=true`。

### 7.2 明确 ServiceConnection 归属

本轮已选择 **CleanCore 原生实现 ServiceConnection**，不再保留“Host/PloyKit 拥有连接、CleanCore 只存 endpoint/auth_ref”这条路线。

确定后的架构边界：

- CleanCore 保存 `ServiceConnection` 的 `base_url/auth_type/auth_ref/network_scope/health/resources`。
- ToolProvider 通过 `service_connection_id` 引用连接；Provider 本身不保存 endpoint 和认证引用。
- HTTP API / Database Adapter operation 通过 `service_connection_id` 引用连接；连接细节不复制到 ToolManifest。
- Host/PloyKit 可以做页面聚合、Secret provider 或 BFF，但不拥有 CleanCore 主模型里的连接事实。

### 7.3 推荐新增/调整字段

`ToolProvider` 当前形态：

```json
{
  "provider_id": "finance_toolhost",
  "provider_type": "static_tool_host",
  "service_connection_id": "conn_finance_toolhost",
  "health": {},
  "sync_policy": {}
}
```

`ToolProvider` 不再保存 `endpoint` 和 `auth_ref`。它们来自 `service_connection_id` 指向的连接资产。开发阶段直接修改 Go 模型、Store、OpenAPI 和测试，不为旧 Provider payload 保留兼容字段。

`ToolManifest` 当前形态：

```json
{
  "tool_id": "customer.lookup",
  "input_schema": {},
  "output_schema": {},
  "risk_level": "low",
  "visibility": "tenant",
  "executor": {
    "type": "static_tool_host",
    "provider_id": "customer_toolhost",
    "operation": "customer.lookup"
  }
}
```

HTTP API 工具当前形态：

```json
{
  "tool_id": "ticket.search",
  "executor": {
    "type": "http_api_adapter",
    "provider_id": "managed_http_api_adapter",
    "operation": "ticket.search"
  }
}
```

对应的 Adapter Provider / operation 保存连接引用和 HTTP 细节：

```json
{
  "provider_id": "managed_http_api_adapter",
  "provider_type": "http_api_adapter",
  "operation": {
    "operation_id": "ticket.get",
    "service_connection_id": "conn_customer_service_api",
    "method": "GET",
    "path": "/customers/{customer_id}/tickets",
    "request_mapping": {
      "path_params": {
        "customer_id": "customer.id"
      },
      "query": {
        "status": "status"
      },
      "headers": {
        "X-Workspace": "workspace_id"
      }
    },
    "response_mapping": {
      "body_path": "data",
      "output": {
        "items": "selected.items",
        "total": "selected.total"
      }
    }
  }
}
```

AdapterOperation 字段必须按 provider_type 分组使用：`http_api_adapter` 只接受 `method/path/headers/request_mapping/response_mapping` 这类 HTTP 字段；`database_adapter` 只接受 `resource_id/query_template/parameter_schema/max_rows/redact_columns/read_only` 这类数据库字段。后端会拒绝两类字段混填，避免一个 operation 同时像 HTTP endpoint 又像数据库查询模板。

HTTP API Adapter 的 `request_mapping` 采用轻量映射，而不是让用户直接写 URL 或脚本：`path_params/query/headers/body` 的值从 ToolCall arguments 的 dot-path 读取。`path` 中出现 `{customer_id}` 这类参数时，必须在 `request_mapping.path_params.customer_id` 显式声明来源；`request_mapping.headers` 不能覆盖平台内部的 `X-Origin-Provider-Auth-Ref`，避免业务参数改写服务连接认证引用。

服务连接资源目录里的 `http_operation`、table/view 仍然不是工具。它们只是 OpenAPI 或数据库发现结果；进入工具目录时调用 `POST /v1/tool-providers/{managed_adapter_id}/operations/from-resource`，由 ToolCatalog 生成 AdapterOperation 草稿，审核后再 publish 成 ToolManifest。`managed_http_api_adapter` 接受 `http_operation`；`managed_database_adapter` 接受 table/view。

代码清理目标：

- 公开 API 不再创建 `executor=http_direct` 工具。
- 删除公开 `ExecutorSpec.url/method/headers` 字段。
- 删除 `HTTPExecutor` 公开运行路径。
- 删除 `disable_http_direct` 配置开关。
- 新建 HTTP API 工具时，实际创建/更新的是 `http_api_adapter` Provider 下的 operation。
- ToolManifest executor 统一使用 Provider 路径，例如 `executor.type=static_tool_host`、`executor.type=agent_plugin_service`、`executor.type=mcp`、`executor.type=http_api_adapter`，并通过 `provider_id + operation` 执行。
- 现有 `http_direct` URL 测试用例直接重写为 `http_api_adapter` 用例。

数据库查询已经走 AdapterOperation -> 内部发布 `ToolManifest.executor=database_adapter` 的路径；HTTP API 工具同样走 AdapterOperation -> 内部发布 `ToolManifest.executor=http_api_adapter`。公开 manifest upsert 仍拒绝手工创建 managed adapter executor：

```json
{
  "provider_id": "managed_database_adapter",
  "operation_id": "orders.query_by_customer",
  "service_connection_id": "conn_orders_db",
  "resource_id": "public.orders",
  "query_template": "select id, total from public.orders where customer_id = :customer_id",
  "parameter_schema": {
    "type": "object"
  },
  "read_only": true,
  "status": "enabled"
}
```

## 8. Schema 对齐与校验

工具 schema 对齐应该分四段做，而不是只相信企业服务声明。

### 8.1 注册时校验

ToolManifest 必须包含：

- `tool_id`
- `name`
- `description`
- `input_schema`
- `output_schema`
- `executor.type`
- 对应 executor 的必要字段

当前后端已有基础校验：缺少 `input_schema` 或 executor 字段会拒绝；启用态 `ToolManifest` 和 `AdapterOperation` 也必须显式声明 `output_schema`。工具可以保存为 `draft` 时缺少 `output_schema`，但进入 `enabled` 前必须补齐。

### 8.2 同步后校验

从 ToolHost/MCP 同步后的工具进入 `synced` 状态，不能直接等于可用。

需要执行：

- JSON Schema 结构合法性校验
- 必填字段检查
- schema 示例生成或示例回放
- smoke test
- 输出结构与 `output_schema` 校验

通过后进入 `validated`，再由管理员启用为 `enabled`。

### 8.3 调用前校验

Agent 调用工具前，运行时必须校验：

- 工具存在
- 工具启用
- Provider 健康
- Agent tool bindings 允许
- 风险策略允许
- 审批策略已满足
- 输入参数匹配 `input_schema`

当前 `ToolRuntime` 已经有 input schema 校验。

### 8.4 调用后校验

工具返回后，运行时必须校验输出是否匹配 `output_schema`。

当前 `ToolRuntime` 已经有 output schema 校验。若失败，应把调用标记为 failed，并记录：

- tool_id
- provider_id
- executor_type
- schema_validation_error
- request_id / trace_id

## 9. 权限与治理边界

### 9.1 全局可见不等于全局可用

工具目录可以是租户全局目录，但这不代表所有 Agent 都能调用。

推荐权限链路：

```text
Tenant 可见
  -> Workspace 可见
  -> ToolManifest enabled
  -> Provider enabled + healthy
  -> Agent tool_bindings allowed
  -> Runtime policy allowed
  -> Human approval if required
```

### 9.2 Agent 不绑定服务连接

Agent 绑定服务连接会造成权限过粗。例如绑定一个客户系统 API 连接后，Agent 是否能调用所有 endpoint 不清楚。

正确做法是：

- 服务连接定义“怎么连”
- 工具定义“能做什么 operation”
- Agent 绑定“允许使用哪些 operation”

### 9.3 HTTP API 工具风险

HTTP API 工具当前由平台内置 HTTP API Adapter Provider 执行。`http_direct` 已退出公开创建入口，不作为长期运行时分支。

HTTP API 工具仍然需要治理：

- 必须引用已启用、健康的 HTTP API 服务连接
- 必须有明确 input/output schema
- 必须 smoke test 成功
- 必须配置超时、重试和最大响应大小
- 高风险操作需要审批策略
- 调用必须进入追踪与审计

原始 URL 配置不作为目标能力保留。开发阶段不做长期迁移读取；测试数据、seed 数据和脚本直接重写为 HTTP API Adapter Provider + operation。

后端治理应围绕 Adapter Provider 生成的 HTTP API 工具展开：

- 允许由 HTTP API Adapter Provider 生成、且引用健康服务连接的 HTTP API 工具
- 拒绝没有健康 ServiceConnection 的 Adapter operation
- 审计记录 provider_id、operation_id、connection_id，而不是记录原始 URL executor

## 10. 状态机建议

### 10.1 服务连接状态

```text
draft -> tested -> healthy -> enabled
                -> unhealthy
enabled -> disabled
```

### 10.2 工具来源状态

当前代码层 `ToolProvider.Status` 只支持 `draft/enabled/disabled`，`health_status` 单独记录健康。下面是产品目标态，可通过状态字段扩展，或通过 `status + health_status + sync_result` 组合表达。

```text
draft -> healthy -> catalog_synced -> validated -> enabled
                         |              |
                         v              v
                      sync_failed     validation_failed
enabled -> disabled
```

### 10.3 工具状态

当前代码层 `ToolManifest.Status` 只支持 `draft/enabled/disabled`。下面是产品目标态，可通过新增状态值实现，也可以先用治理视图中的校验结果表达。

```text
draft -> synced/imported -> validated -> enabled
                              |
                              v
                         validation_failed
enabled -> disabled -> deprecated
```

### 10.4 Agent 绑定状态

Agent 工具绑定应跟随 Agent 草稿/版本发布：

```text
draft binding -> release review -> active version binding
```

不要因为一个工具存在于目录，就自动进入所有 Agent 的 active binding。

### 11.2 新建服务连接

第一步选择类型：

- HTTP API
- Database
- Webhook

- OAuth

- 默认超时、重试、响应大小上限
- 权限范围说明

不要出现：

- ToolHost

- HTTP API 工具创建

第一步选择方式：

- 展示同步出的工具清单

## 13. 实施阶段

### Phase 1：前端概念整理与 ServiceConnection 主干

- 菜单改名：工具 -> 工具目录，企业工具服务 -> 工具来源。
- 服务连接页只展示连接资产。
- CleanCore 已补齐 ServiceConnection 后端主干和 HTTP API AdapterOperation 主链路；HTTP API 工具入口放在工具目录，通过选择服务连接创建/发布 operation。
- Agent 创建页只选择具体工具，不选择工具来源/服务连接。
- 文案明确：Agent 可不带技能和工具创建。

### Phase 2：补齐 Adapter Provider

- `ServiceConnection` 已归属 CleanCore 主干。
- `ToolProvider` 已支持 `service_connection_id`，公开 `endpoint/auth_ref` Provider 字段已从 Go 模型、Store、OpenAPI 和测试中移除。
- ServiceConnection/ToolProvider 健康字段已收敛为只读观测：普通 upsert 不保存调用方传入的健康值，只有 connection test / provider health 写入；连接或 provider 的健康范围变化时重置为 `unknown`。
- 已新增平台内置 `http_api_adapter`；`database_adapter` 已具备定义、存储、Postgres 资源发现、只读 SQL 执行和基础结果列脱敏主干。
- `ExecutorSpec` 已只走 `provider_id + operation` 的 Provider 路径，不保留公开 `http_direct`。
- `parseToolExecutorSpec`、`validateManifest`、`buildExecutor`、OpenAPI、测试用例已同步删除 `url` 模型。
- `HTTPExecutor`、`disable_http_direct` 和相关 e2e 脚本路径已删除。
- 工具目录展示 connection/provider 引用关系。

### Phase 3：数据库工具生成

- Database service connection 支持资源发现。
- 查询模板字段已进入 AdapterOperation；后续可按复杂度拆出独立 QueryTemplate 模型。
- Database Adapter Provider 已进入主干；复杂写操作或跨系统编排仍建议通过 ToolHost/MCP 标准化封装。
- 工具目录支持从数据库连接生成查询工具。
- 后续增强数据库工具策略脱敏和运行审计。

## 14. 待决策问题

1. MCP 输出已按 `structuredContent` 优先归一化为业务对象；后续只需评估是否增加显式切换策略。
2. HTTP API/数据库工具统一走平台固定内置 Adapter Provider：`managed_http_api_adapter`、`managed_database_adapter`。公开 ToolProvider 创建页只保留 AgentPlugin Service、ToolHost、MCP，不再公开 `http_direct` 或让用户创建业务命名的 Adapter Provider。
3. 是否需要全局技能库？当前技能更偏 Agent scoped，和工具目录不是同一层概念。

## 15. 最终推荐口径

推荐对产品和前端统一使用下面这套话术：

- **服务连接**：我怎么连到一个外部系统。
- **工具来源**：我从哪里同步一批工具，并由谁执行这些工具。
- **工具目录**：平台里有哪些具体可调用工具。
- **Agent 工具绑定**：这个 Agent 被允许调用哪些具体工具。

对应用户路径：

```text
需要复用外部 endpoint/认证时，先建服务连接
  -> 再接入工具来源，或创建平台内置 Adapter operation
  -> 工具进入工具目录
  -> 管理员治理和测试
  -> Agent 绑定具体工具
  -> 运行时按 schema、权限、审批、审计执行
```

这能解决“先有鸡还是先有蛋”的问题：Agent 可以先创建为空壳；工具也可以先进入目录；两者通过后续绑定关联，不要求创建时互相依赖。
