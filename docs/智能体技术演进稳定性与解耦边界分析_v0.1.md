# 智能体技术演进、稳定性与解耦边界分析

版本：v0.1
日期：2026-06-04
定位：面向 Agent Runtime / CleanCore 架构演进的技术判断文档

---

## 0. 核心结论

智能体系统确实应该解耦，但不是“越解耦越好”。更准确的原则是：

```text
按变化原因解耦，而不是按对象名解耦。
把不变量收进内核，把易变量放到策略、包、适配器和运行时数据层。
```

过去几年 Agent 技术变化很快：ReAct 把推理和行动交错起来，Toolformer 把工具调用变成模型可学习能力，Reflexion / Voyager 强调反思、记忆和技能库，AutoGPT 一类项目把自主循环推到台前，LangGraph / Agents SDK / Semantic Kernel / AutoGen / CrewAI 等框架开始生产化，MCP 和 A2A 又把工具互联、智能体互联推进为协议层问题。

但纵观这些变化，真正稳定的不是某个 Agent 框架，也不是某种 planner，而是下面这些系统不变量：

```text
1. Agent 需要一个受控运行生命周期。
2. 模型输出不能直接成为事实，必须经过结构化解析和校验。
3. 工具调用必须有 schema、权限、审批、幂等、结果校验和审计。
4. 长任务必须有状态、事件、checkpoint、恢复和 replay。
5. Prompt / Context 只是事实投影，不是事实源。
6. 模型、工具协议、记忆策略、规划策略、安全策略都会持续变化。
7. 外部协议只能通过 adapter 进入系统，不能反向污染 Runtime Core。
```

所以，对 CleanCore 这类平台型系统来说，推荐的方向是：

```text
稳定内核 + 可版本化契约 + 策略驱动 + 外部适配器 + 运行事实可追踪
```

一句话：

```text
不要把“当前流行的 Agent 写法”做成内核。
要把“所有 Agent 都绕不开的治理链路”做成内核。
```

## 1. 智能体技术演进简史

### 1.1 前 LLM 时代：Agent 是控制系统

早期 Agent 主要来自符号 AI、规划、BDI、工作流、RPA、强化学习和多智能体系统。它们的共同点是：

```text
感知环境
维护状态
根据目标选择行动
执行动作
观察反馈
```

这个时期稳定下来的不是具体算法，而是控制系统视角：

```text
Agent = 状态 + 目标 + 决策 + 动作 + 反馈
```

这套结构今天仍然成立，只是“决策器”从规则、规划器、策略网络，换成了大模型。

### 1.2 2022：ReAct 让推理和行动交错

ReAct 的关键变化是：让模型在同一个轨迹里交错生成 reasoning trace 和 action。论文中强调，reasoning trace 帮助模型维护和调整行动计划，action 让模型连接外部知识源或环境。

这件事奠定了现代 LLM Agent 的基本循环：

```text
Observe
  -> Think / Decide
  -> Act
  -> Observe result
  -> Continue or Finish
```

稳定下来的部分：

```text
模型需要外部工具。
工具结果会改变下一步推理。
Agent 不是一次性问答，而是多步闭环。
```

不稳定的部分：

```text
是否暴露 chain-of-thought。
推理轨迹是否写入 prompt。
Think / Act 格式如何表达。
模型是否内建 tool calling。
```

### 1.3 2023：工具使用、反思、记忆和自主循环爆发

2023 年的关键趋势是：Agent 从“能调用工具”走向“能组织多步任务”。

Toolformer 证明模型可以学习“什么时候调用 API、调用什么、传什么参数、如何利用结果”。Reflexion 强调通过语言化反馈做 trial-and-error 学习。Voyager 在 Minecraft 环境里把探索、代码技能库和长期记忆结合起来。AutoGPT / BabyAGI 一类项目则把自主任务循环变成大众认知里的 Agent 形态。

这一阶段暴露出很多问题：

```text
无限循环
工具误调用
任务漂移
上下文膨胀
记忆污染
成本失控
幻觉行动
权限边界模糊
```

因此，真正被验证出来的工程结论不是“Agent 越自主越好”，而是：

```text
自主循环必须被状态机、预算、权限、审计和停止条件约束。
```

### 1.4 2024：从 demo 走向运行时、评测和可靠性

2024 年的主线是生产化。行业开始意识到，Agent 的瓶颈不只是模型能力，而是：

```text
长任务可恢复
人类介入
状态持久化
工具安全
观测和回放
评测闭环
```

LangGraph 的定位很有代表性：它把自己定义为低层 orchestration runtime，重点放在 durable execution、streaming、human-in-the-loop、persistence 等能力上，而不是只提供一个更花哨的 prompt 框架。

同一时期，WebArena、OSWorld 等 benchmark 也说明，真实 Web / 真实桌面环境里的 Agent 成功率远低于人类，问题集中在 GUI grounding、操作知识、长任务稳定性、环境反馈和执行可靠性。

这一阶段的工程启发：

```text
Agent 不是“更聪明的 prompt”，而是“模型驱动的分布式执行系统”。
```

### 1.5 2025-2026：协议化、平台化、安全治理

2025 以后，技术变化继续加速，但变化重心开始从“单个 Agent 怎么写”转移到“Agent 生态怎么互联”。

MCP 标准化的是 LLM 应用和外部工具、资源、上下文之间的连接。A2A 标准化的是不同框架、不同厂商、彼此不透明的 Agent 系统之间如何发现能力、交换任务、协作和保持安全边界。

OpenAI Agents SDK 这类框架也把 primitives 收敛到少数核心概念：

```text
Agent
Tool
Handoff / Agents as tools
Guardrails
Tracing
```

这些趋势说明：生态层在变，但大家都在向同一批工程原语收敛。

## 2. 哪些东西变动不大

下面这些是建议放进 Runtime Core 或强契约层的稳定部分。

### 2.1 AgentRun / Task 生命周期

无论 planner 怎么变，Agent 都需要：

```text
created
running
waiting_input
waiting_approval
completed
failed
cancelled
```

说明：这是通用运行生命周期的稳定抽象。CleanCore 当前 `RunStatus` 实际为
`created / running / waiting_input / waiting_approval / completed / failed / cancelled`；
超时通过 `CodeModelTimeout` 等错误进入 `failed`，尚未建模为独立 `timed_out` 状态。

稳定原因：

```text
这是运行事实，不是模型策略。
这是恢复、审计、回放、统计、计费、SLA 的基础。
```

设计建议：

```text
Task / Run 状态机进入内核。
状态变更只能由 Kernel 或受控 command 追加。
任何 planner / hook / tool executor 都不能直接改状态。
```

### 2.2 ToolCall / ToolResult 基本语义

工具协议会变，但工具调用的核心语义变化不大：

```text
tool_id
tool_version
input_schema
arguments
caller
scope
risk_level
approval_status
execution_domain
result
error
artifact_refs
trace_id
idempotency_key
```

说明：这是治理语义清单，不等于所有字段都必须放在 `ToolCall` 一个结构中。
CleanCore 当前 `ToolCall` 已包含 `tool_id / arguments / trace_id / run_id / task_id / idempotency_key`；
`tool_version` 主要来自 `ToolDefinition.Version` 和 `AgentRun.VersionSnapshot.ToolDefinitions`，
`approval_status` 由 `ToolResult.Status = pending_approval` 表达，
`execution_domain` 由 `ToolDefinition.ExecutionProfile` 和执行 trace 表达。
如果未来要做严格 replay，应考虑把实际调用时的 tool version / execution profile snapshot 写入 call 或 result。

稳定原因：

```text
模型要行动，就必须把不确定文本变成可治理命令。
工具有副作用，就必须被权限、幂等、审计和结果校验包住。
```

设计建议：

```text
ToolManifest / ToolCall / ToolResult 进入强契约。
MCP、HTTP、worker、managed runtime 只是 executor adapter。
模型永远不能直接访问外部 endpoint。
```

### 2.3 决策必须结构化和可校验

模型输出天然不可靠。无论是 ReAct 文本、function calling、JSON schema、Responses API、OpenAI / Anthropic / Gemini / DeepSeek 等模型格式，系统都必须把模型输出转成内部 Decision。

稳定的 Decision 语义包括：

```text
reply / answer
tool_call
ask_clarification
refusal
policy_notice
no_op
unsupported
error
```

说明：CleanCore 当前内部 `DecisionType` 为 `reply / no_op / ask_clarification / tool_call / unsupported / error`。
`refusal`、`policy_notice` 通过 `reply.kind` 表达；内部 Agent 协作不是独立 `handoff` Decision，
而是由 `tool_call` 调用 `origin.agent.delegate` 后进入 `AgentHandoff` 生命周期。

设计建议：

```text
Decision 是内部契约，不等于某个模型 API 的返回格式。
每个模型 provider 都只负责适配到 DecisionCandidate。
DecisionValidator 再决定能否进入 dispatch。
```

### 2.4 Policy / Approval / Audit 必经链路

安全威胁会变，但下面的治理形态非常稳定：

```text
是否允许看见某工具
是否允许调用某工具
是否需要审批
是否允许自动重试
是否允许写 memory
是否允许跨 Agent 传上下文
是否允许访问外部网络 / 文件 / shell
```

OWASP 2025 LLM Top 10 把 prompt injection、sensitive information disclosure、supply chain、improper output handling、excessive agency 等列为核心风险。MCP 规范也强调工具代表任意代码执行路径，需要用户同意、数据隐私和工具安全控制。

设计建议：

```text
Policy 不做成 prompt。
Policy 不做成工具 executor 内部逻辑。
Policy 必须在 Kernel -> ToolRuntime -> ExecutionDomain 主链路上强制执行。
```

### 2.5 事实源和上下文投影分离

这个边界非常关键，也最容易被 Agent 项目搞乱。

稳定事实源：

```text
TaskEvent
RunEvent
ToolResult
Artifact
MemoryRecord
TraceEvent
AuditEvent
AgentDefinition version
Policy version
ToolManifest version
```

运行时投影：

```text
WorkView
PromptBundle
ToolCard
MemorySummary
ArtifactSummary
CollaboratorCard
```

设计建议：

```text
PromptBundle 不是事实源。
WorkView 不是长期存储。
模型输出不是事实。
工具返回不是可信事实，必须被校验和记录。
```

### 2.6 版本钉住、回放和可比较 Eval

Agent 技术会不断更新，所以更需要版本钉住：

```text
AgentDefinition version
Policy version
ToolManifest version
Model provider / model version
PromptBundle hash
Decision schema version
Evaluator version
```

稳定原因：

```text
没有版本钉住，就没有可靠回放。
没有可靠回放，就无法定位回归。
没有可比较 Eval，就无法判断优化是不是有效。
```

## 3. 哪些东西最容易变

下面这些不建议写死进内核。

### 3.1 模型供应商、模型能力和 API 形态

高频变化包括：

```text
模型名称和上下文窗口
tool calling 格式
structured output 能力
reasoning effort / thinking budget
多模态输入输出
computer use / browser use
parallel tool calls
内置 web search / file search / code interpreter
流式事件格式
价格、速率限制、区域合规
```

设计建议：

```text
ModelClient 是 adapter。
核心只认 ModelRequest / ModelResponse / DecisionCandidate。
模型能力通过 ModelCapabilityDescriptor 暴露，不能散落在业务代码里。
```

### 3.2 Prompt 组织方式

Prompt 会持续变化：

```text
system / developer / user 分层
few-shot 示例
工具卡格式
是否显式 ReAct
是否暴露 scratchpad
上下文压缩策略
长上下文排序
安全提示词
输出格式约束
```

设计建议：

```text
PromptBuilder 可替换。
PromptBundle 必须有 hash。
prompt 优化必须进入 AgentPackage / Policy / Eval 流程，而不是热改线上定义。
```

### 3.3 Planner / Reasoner

变化非常快：

```text
ReAct
Plan-and-Execute
Tree of Thoughts
Reflexion
self-consistency
multi-sample search
verifier-guided search
task graph planner
workflow planner
learned planner
```

设计建议：

```text
Planner 是策略，不是内核。
Planner 可以产生 PlanStep / hints / candidate actions。
最终能不能执行，仍由 DecisionValidator + Policy + ToolRuntime 决定。
```

### 3.4 Memory / RAG / Context Ranking

长期记忆是最不稳定的模块之一：

```text
向量库
BM25 / hybrid search
knowledge graph
episodic memory
semantic memory
procedural memory
summary memory
profile memory
memory write policy
memory decay / forgetting
```

稳定的是 MemoryRecord 的治理语义，不稳定的是召回、排序、摘要、写入策略。

设计建议：

```text
MemoryStore、Retriever、Ranker、Summarizer、WritePolicy 分开。
Memory 写入必须经 policy。
模型不能直接写长期记忆，只能提出 memory_write_intent。
```

### 3.5 工具接入协议

工具会从本地函数变成 HTTP、MCP、worker、queue、browser、shell、sandbox、managed tools、enterprise connectors。

设计建议：

```text
核心抽象稳定在 ToolManifest / ToolCall / ToolResult。
MCP 只是 ToolProvider adapter。
HTTP 只是 transport。
工具目录是 source of truth，RuntimeRegistry 只是可执行缓存。
```

### 3.6 Agent-to-Agent 协作方式

多 Agent 协作会持续演进：

```text
handoff
agent as tool
supervisor / worker
debate
market / bidding
blackboard
task graph
A2A remote agent
human-agent hybrid team
```

设计建议：

```text
内部 Agent 协作走 AgentHandoff。
固定能力导出走 AgentExportedTool。
外部 Agent 协议走 A2A adapter。
不要用一个 other_agents 字段混掉协作、授权、能力导出和外部接入。
```

### 3.7 安全防护策略

攻击方式和防护手段都会持续变化：

```text
prompt injection
tool poisoning
data exfiltration
indirect prompt injection
malicious tool description
memory poisoning
excessive agency
supply chain attack
model-specific jailbreak
```

设计建议：

```text
安全策略可版本化。
高风险动作默认审批。
工具描述、外部资源、检索内容都按不可信输入处理。
权限不靠 prompt 表达，必须在执行链路强制。
```

## 4. 最应该解耦的模块

### 4.1 Model Runtime

解耦原因：

```text
外部供应商变化快。
模型能力变化快。
API 兼容性不可控。
成本和延迟策略经常调整。
```

边界建议：

```text
internal/model/client
  ModelClient
  ModelRequest
  ModelResponse
  ModelCapabilityDescriptor
  ProviderAdapter
```

禁止：

```text
业务模块直接拼 provider-specific payload。
ToolRuntime 依赖某个模型 SDK。
DecisionValidator 识别某个厂商私有格式。
```

### 4.2 Tool Provider / Execution Adapter

解耦原因：

```text
工具数量增长快。
协议变化快。
执行环境风险高。
外部工具不可信。
```

边界建议：

```text
ToolManifest 是定义。
ToolRuntime 是治理入口。
ExecutorAdapter 是执行后端。
ExecutionDomain 是隔离环境。
```

适配器可以包括：

```text
go_builtin
http_direct
static_tool_host
mcp
worker
queue
browser
shell
managed_tool
agent_tool
```

### 4.3 Context Engine / Prompt Builder

解耦原因：

```text
上下文窗口变化快。
prompt 策略变化快。
memory / tool / collaborator 的投影格式变化快。
```

边界建议：

```text
事实源 -> WorkView -> PromptBundle -> ModelRequest
```

关键约束：

```text
WorkView 和 PromptBundle 只读事实，不写事实。
PromptBundle 必须可 hash、可回放、可 diff。
```

### 4.4 Planner / Runtime Hook

解耦原因：

```text
planner 技术路线不稳定。
不同 Agent 需要不同任务策略。
```

推荐方式：

```text
先开放 Data Hook / Strategy Hook。
暂缓开放完整 RuntimeDriver。
```

Hook 可以做：

```text
候选排序建议
上下文补丁
planner hints
memory write intents
risk hints
```

Hook 不能做：

```text
推进 run 生命周期
直接执行工具
直接写 task / memory / trace
绕过 policy / approval
```

### 4.5 Memory Service

解耦原因：

```text
记忆技术路线多。
业务隐私和保留策略差异大。
召回质量高度依赖场景。
```

边界建议：

```text
MemoryRecord: 稳定事实
MemoryRetriever: 可替换
MemoryRanker: 可替换
MemorySummarizer: 可替换
MemoryWritePolicy: 可版本化
```

### 4.6 Agent Collaboration Adapter

解耦原因：

```text
A2A / ACP / 自研协议 / 企业消息系统都会并存。
内部 Agent 和外部 Agent 的信任边界不同。
```

边界建议：

```text
Internal Handoff != External A2A
Agent exported tool != Agent collaborator
Agent card != internal AgentDefinition
```

### 4.7 Eval / Observability / Replay

解耦原因：

```text
benchmark 会变化。
业务指标会变化。
模型能力变化后评价标准会变化。
```

但主链路必须固定写 trace / audit：

```text
TraceEvent / AuditEvent 是稳定事实。
Evaluator / Grader / Report 是可替换分析层。
```

## 5. 不应该过度解耦的部分

### 5.1 Runtime Kernel 主循环

不要过早把主循环插件化。否则会出现：

```text
谁负责 step limit？
谁负责 approval？
谁负责 tool policy？
谁负责 trace？
谁负责 run terminal state？
谁负责 recovery？
```

建议：

```text
Kernel 保持唯一控制面。
Planner / Hook 只能提供建议。
Kernel 决定是否执行和如何落状态。
```

### 5.2 Policy 必经点

Policy 不应该被拆成各模块自觉执行，否则必然漏。

正确做法：

```text
所有高风险路径收敛到少数 choke points：
ToolRuntime.Invoke()
MemoryService.Write()
AgentHandoff.Create()
PackagePublish()
ExternalToolsInvoke()
```

### 5.3 运行事实写入

不要让 executor、hook、planner 到处写状态。

正确做法：

```text
状态写入必须由领域服务完成。
外部模块只能返回 result / intent / patch。
```

### 5.4 内部契约

不要为了兼容所有外部协议，把内部契约设计成“万能 JSON”。

正确做法：

```text
内部契约窄而强。
外部协议宽而杂。
宽杂协议通过 adapter 映射到窄强契约。
```

## 6. 稳定性矩阵

| 模块 | 变化速度 | 稳定内容 | 易变内容 | 建议边界 |
| --- | --- | --- | --- | --- |
| Runtime Kernel | 低 | run/step 生命周期、停止条件、dispatch | 完整自定义 runtime | 保持内核，不开放控制流插件 |
| Task State | 低 | 状态机、事件追加、恢复 | 业务任务类型 | 内核事实层 |
| Decision | 中 | reply/tool_call/ask_clarification/no_op/unsupported/error；refusal/policy_notice 由 ReplyKind 表达；handoff 由工具调用进入 AgentHandoff | 模型输出格式 | parser/validator 解耦 |
| Model Runtime | 高 | 请求/响应抽象、能力描述 | provider、模型名、API、tool calling | adapter 强解耦 |
| Prompt Builder | 高 | PromptBundle hash、token budget | 组织格式、few-shot、压缩策略 | strategy 解耦 |
| Context Engine | 中高 | 事实投影边界 | 排序、摘要、裁剪 | WorkView / PromptBundle 分层 |
| Planner | 高 | PlanStep / hint 语义 | ReAct、ToT、Reflexion、多采样 | Policy/Hook 解耦 |
| Tool Manifest | 中 | schema、risk、visibility、version | provider protocol、transport | manifest 稳，executor adapter 变 |
| Tool Runtime | 低 | schema/policy/approval/trace/result | 具体 executor | 核心治理入口 |
| Execution Domain | 高 | 隔离、权限、资源限制 | docker、sandbox、browser、managed runtime | domain adapter |
| Memory | 高 | MemoryRecord、scope、write audit | retrieval、ranking、summarization | store/retriever/ranker 分离 |
| Agent Package | 中 | draft/publish/version/rollback | metadata、skills、prompt 格式 | package 编译边界 |
| Multi-Agent | 高 | handoff/task/artifact/context package | A2A、agent-as-tool、team topology | 内外协作分离 |
| Policy | 中高 | 必经链路、版本、审计 | 规则、风险模型、审批条件 | policy set 可版本化 |
| Eval | 高 | run snapshot、trace、dataset version | benchmark、grader、指标 | eval harness 解耦 |
| Observability | 中 | trace/audit/metrics 基本事件 | 可视化、分析、自动修复 | 事件稳定，分析可变 |

## 7. 对 CleanCore 的架构判断

从现有 CleanCore 文档和代码方向看，当前架构已经抓住了几个正确核心：

```text
AgentPackage / AgentDefinition / AgentRun / Task 分离
WorkView / PromptBundle 作为运行时投影
Decision Parser / Validator 作为模型输出闸门
ToolRuntime 统一做 schema / policy / approval / trace
AgentHandoff 和 Agent exported tool 分开
Runtime Hook 先做 data hook，不开放 control-flow plugin
Trace / Audit / Eval / Release 作为治理闭环
```

这些方向值得继续坚持。

### 7.1 建议明确写入架构总原则

建议把下面这段作为 CleanCore 后续演进原则：

```text
CleanCore 不追随某个 Agent 框架的表层写法。
CleanCore 只固化 Agent 运行治理的不变量。
模型能力、工具协议、规划策略、记忆策略、协作协议、安全策略
全部通过可版本化策略、包定义、adapter 或 hook 接入。
```

### 7.2 推荐模块边界

```text

  内部强契约：Run / Task / Decision / Tool / Policy / Handoff / Artifact / Trace

agent-definition
  AgentPackage draft/publish/stable/rollback

  go/http/mcp/worker/browser/sandbox/managed adapters
```

### 7.3 依赖规则

必须禁止的依赖：

```text

```

## 8. 解耦设计的实操标准

判断一个模块是否应该解耦，可以问五个问题。

### 8.1 变化是否由外部驱动

如果变化来自模型厂商、协议标准、外部服务、安全威胁、云平台，就强解耦。

典型模块：

```text
model provider
MCP adapter
A2A adapter
external tool provider
execution sandbox
security detector
```

### 8.2 变化是否影响安全边界

如果模块一变就可能绕过权限、泄露数据、扩大副作用，必须解耦且加 choke point。

典型模块：

```text
tool execution
memory write
handoff context
external invoke
package publish
approval
```

### 8.3 是否需要 A/B、灰度和 Eval 比较

需要频繁实验的东西不要写进内核。

典型模块：

```text
prompt
planner
memory retriever
tool ranker
repair strategy
context compression
```

### 8.4 是否是运行事实

如果是事实源，不要过度插件化。

典型模块：

```text
TaskEvent
RunEvent
ToolResult
Artifact
TraceEvent
AuditEvent
```

### 8.5 是否有多个成熟实现会长期并存

长期并存就做 adapter。

典型模块：

```text
OpenAI / Anthropic / Gemini / DeepSeek / local model
MCP / HTTP / gRPC / queue
Postgres / object storage / vector db
Docker / Firecracker / browser / managed runtime
```

## 9. 推荐演进路线

### Phase 1：冻结核心不变量

目标：

```text
Run / Task / Decision / ToolCall / ToolResult / Policy / Trace / Audit 契约稳定。
```

关键动作：

```text
1. 明确 Runtime Kernel 唯一控制面。
2. 明确 ToolRuntime 是所有工具执行唯一入口。
3. 明确 PromptBundle / WorkView 不是事实源。
4. 明确模型输出必须经过 DecisionValidator。
5. 明确 AgentRun 钉住 AgentDefinition / Policy / ToolManifest / PromptBundle hash。
```

### Phase 2：强化易变层 adapter

目标：

```text
让易变技术可以替换，但替换不破坏运行事实。
```

关键动作：

```text
1. ModelProvider adapter + capability descriptor。
2. ToolProvider adapter：HTTP / static_tool_host / MCP。
3. Memory retriever/ranker/summarizer/write policy 分离。
4. PlannerPolicy / ToolRankingPolicy / ContextPolicy 版本化。
5. A2A adapter 放在外部 collaboration boundary，不进入 Kernel。
```

### Phase 3：建立 Eval 驱动的变更系统

目标：

```text
任何 prompt、policy、planner、memory、tool、model 变化，都能通过 Eval / Replay 判断收益和回归。
```

关键动作：

```text
1. 每个 AgentPackage 发布必须绑定 eval suite。
2. 每个 ToolManifest 变更必须有 contract test。
3. 每个 PolicySet 变更必须有安全回归用例。
4. 每个 ModelProvider 切换必须有 replay comparison。
5. 每个 RuntimeHook 上线必须有 trace / audit / diff。
```

### Phase 4：谨慎开放 RuntimeDriver

只有当多个真实业务 Agent 都需要完全不同控制流时，再开放完整 RuntimeDriver。

开放前置条件：

```text
1. Driver 不能绕过 policy / approval。
2. Driver 不能绕过 trace / audit。
3. Driver 必须遵守 run / task 生命周期。
4. Driver 必须支持 replay / recovery。
5. Driver 输出必须仍然是内部 Decision / ToolCall / ToolResult。
```

## 10. 最终回答：哪些不变、哪些易变、哪些最好解耦

### 10.1 变动不大的

```text
AgentRun / Task 生命周期
状态机和事件追加
ToolCall / ToolResult 治理语义
Decision 结构化校验
Policy / Approval / Audit 必经链路
版本钉住和 replay
事实源与 prompt 投影分离
runtime limit / budget / stop condition
artifact / memory 引用化管理
```

这些应该进入内核或强契约。

### 10.2 容易变动的

```text
模型供应商和模型 API
tool calling 格式
prompt 组织方式
planner / reasoner 算法
memory / RAG 策略
工具接入协议
多 Agent 协作协议
安全检测和防护策略
benchmark / evaluator
UI 和 human-in-the-loop 产品形态
```

这些应该进入 adapter、policy、hook、package 或 eval 层。

### 10.3 最好解耦的

优先级从高到低：

```text
1. Model Runtime
2. Tool Provider / Executor Adapter
3. Execution Domain / Sandbox
4. Context Engine / Prompt Builder
5. Memory Retriever / Ranker / WritePolicy
6. Planner / Runtime Hook
7. Agent Collaboration / A2A Adapter
8. PolicySet / Approval Strategy
9. Eval / Grader / Benchmark
10. Observability Analysis / Auto-repair
```

### 10.4 不要过度解耦的

```text
Runtime Kernel 主循环
Task / Run 状态事实
ToolRuntime 治理入口
Policy 必经点
Trace / Audit 写入
版本钉住
Release / rollback 语义
```

这些一旦碎片化，系统会看似灵活，实际失去可治理性。

---

## 11. 总结

智能体技术未来还会继续变。模型会更强，工具协议会更标准，多 Agent 会更普遍，记忆和规划会继续换代，安全攻防也会持续升级。

但平台架构不能跟着每一波表层技术摆动。真正抗变化的 Agent Runtime 应该把下面这句话贯彻到底：

```text
易变能力都可插拔，关键事实都可追踪，所有副作用都可治理。
```

对 CleanCore 来说，最合理的技术路线不是追求“最大解耦”，而是追求：

```text
最小稳定内核
+ 明确强契约
+ 外部 adapter
+ 策略版本化
+ Eval 驱动变更
+ Trace / Audit / Replay 托底
```

这会比追某个 Agent 框架更慢一点，但会更耐用。
