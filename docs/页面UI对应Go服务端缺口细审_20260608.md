# 页面 UI 对应 Go 服务端缺口细审（Origin AgentOps）

审计日期：2026-06-08  
审计目标：按当前 Origin AgentOps 页面 UI，核对 PloyKit Origin 模块接口与 Go CleanCore 服务端能力，明确“Go 真缺失”“Go 已有但未接入”“PloyKit 本地降级假实现”“前端未绑定”。

## 结论先行

当前不是“Go 服务端完全缺失”。Go CleanCore 已有一批可复用能力：`agent.run`、AgentPackage draft/review/publish/canary/stable/rollback、Prompt preview、tool provider/group/manifest、runtime hook、policy、approval approve/reject、eval、trace、usage evidence 等，证据见 `server.go:5252-5423` 和 `openapi.clean-core.v1.json:6950-7018`。

真正的问题分四类：

| 分类 | 结论 | 典型例子 |
| --- | --- | --- |
| Go 已有但 Origin 模块未接 | 需要改 PloyKit Origin API/action 或前端映射，不一定要新写 Go | Agent 详情页的 prompt-profile、tool-bindings、skills、collaborators、exported-tools、versions，Go 有 `/v1/agents/{id}/...`，但 Origin UI 仍主要读本地 `agents` 表。 |
| Go 侧真缺口 | 需要 Go 增加 REST/command 或扩展查询模型 | 全局搜索、列表统一分页过滤、运行取消、导出报表、审批规则管理、Trace 保存视图、Usage 账单/额度管理。 |
| PloyKit 本地降级假实现 | PloyKit 调了 CleanCore，但失败后仍写本地表并显示成功 | `runAgent`、`publishAgent`、`syncCatalog`、`smokeInvoke`、`checkServiceConnection`、`traces POST` 等。 |
| 前端 UI 未绑定 | 不属于 Go 缺失，先要前端补动作或隐藏按钮 | 顶栏搜索、通知、帮助、收藏、复制、导出、分页按钮、更多筛选、模板下载。 |

### G-01 顶栏全局搜索没有服务端接口

| 项目 | 细节 |

| 建议补齐 | Go 增加 `GET /v1/search?q=&types=agents,tools,runs,traces&limit=&cursor=`；PloyKit Origin 增加 `/origin-agentops/search` 转发；UI 顶栏绑定输入、防抖、结果弹层。 |

### O-02 发起运行显示成功，但可能只是本地 run 记录

| 项目 | 细节 |
| --- | --- |
| UI 设计 | 概览页和 Agent 页可以发起运行。 |
| PloyKit 当前 | UI 调 `/api/modules/origin-agentops/runs`；PloyKit 再调 CleanCore `/v1/commands` command=`agent.run`，无论 CleanCore 是否可用，都会插入本地 `runs` 记录。 |
| Go 当前 | Go 支持 `agent.run`，并进入 `Coordinator.HandleEnvelope()`。 |
| 缺口归属 | Go 能力已有；PloyKit 降级逻辑导致“真实执行”和“本地成功”混淆。 |
| 影响 | CleanCore 未配置时，UI 仍显示 run succeeded/waiting/running，用户会误以为真实 agent 已执行。 |
| 建议补齐 | PloyKit 需要区分 `cleanCore.ok=true` 的真实运行和 `cleanCore.ok=false` 的 demo run；UI 增加“降级演示数据”标识；必要时禁止生产环境降级写成功。 |
| 证据 | `api/runs.ts:23-108`、`server.go:5257-5270`、`cleancore.ts:8-50`。 |

### O-03 发布、同步、审批动作没有完全复用 Go 的正式流程

| 项目 | 细节 |
| --- | --- |
| UI 设计 | 概览页可发布草稿、同步工具、审批通过。 |
| PloyKit 当前 | `publishAgent` 调 `agent.package.publish`，但之后更新的是 PloyKit 本地 `agents` 表；`syncCatalog` 调 `tool.provider.sync`，但也会本地 upsert 一个 smoke tool；`resolveApproval` 调的是 `/v1/approvals/{id}` PATCH。 |
| Go 当前 | Go command 支持 `agent.package.publish`、`tool.provider.sync`、`approval.approve/reject`；但 Go REST 路由中没有 `/v1/approvals/{id}` PATCH。 |
| 缺口归属 | 部分 Go 已有但 PloyKit 调错/未细接；审批 REST 是 Go 缺失或 PloyKit 调用路径错误。 |
| 影响 | 发布和同步可能只是本地状态变更；审批 action 调 Go `/v1/approvals/{id}` 很可能失败后本地更新。 |
| 建议补齐 | `resolveApproval` 应改为 `/v1/commands` command=`approval.approve` 或 `approval.reject`；发布应使用 `draft_id` 路径并回读 Go release；同步应使用 Go 返回的 tools 而不是固定生成 smoke tool。 |
| 证据 | `actions/publish-agent.ts:11-37`、`actions/sync-catalog.ts:11-49`、`actions/resolve-approval.ts:12-16`、`server.go:5316-5319`、`server.go:5384-5391`、`server.go:5410-5413`。 |

### A-02 Agent 创建没有映射到 Go 的完整 AgentPackage draft 流程

| 项目 | 细节 |
| --- | --- |
| UI 设计 | 新建 Agent 包含 prompt、skills、tools、provider、审批、外部 API、trace 等配置。 |
| PloyKit 当前 | `POST /origin-agentops/agents` 调 Go `/v1/agents`，payload 中塞 `prompt_profile/skills/tool_bindings/governance_summary`，然后本地 upsert `agents` 表。 |
| Go 当前 | `/v1/agents` 的 `handleAgentCreate()` 主要创建 AgentAsset；只有当 payload 有 `version/prompt/agents_md` 时才创建 draft。它不按 PloyKit 的 `prompt_profile/skills/tool_bindings/governance_summary` 字段完整落 draft 子资源。 |

| 证据 | `api/agents.ts:38-170`、`server.go:529-567`、`server.go:5340-5383`。 |

### A-03 Agent 删除在 Go 侧不是彻底删除语义

| 项目 | 细节 |
| --- | --- |
| UI 设计 | Agent 列表“更多/删除”表现为删除 Agent。 |
| PloyKit 当前 | UI 调 `DELETE /origin-agentops/agents/{agentId}`，随后本地数据删除或隐藏。 |
| Go 当前 | `handleAgentDelete()` 调 `DeleteAgentAssetForTenant()`，但静态 registry 中的内置 Agent 仍可能通过 `synthesizedAgentAsset()` 被重新合成出来。 |
| 缺口归属 | Go 删除语义需要确认；PloyKit UI 文案也需要明确是删除、禁用还是归档。 |
| 影响 | 用户以为删除成功，但 Go 侧内置 Agent 可能仍可见或可运行。 |
| 建议补齐 | 定义 Agent lifecycle：delete、disable、archive 分开；Go 提供 disabled projection 或 tombstone；UI 文案改成“禁用/归档”更准确。 |
| 证据 | `AgentOpsApp.tsx:3523-3535`、`server.go:642-648`、`server.go:579-584`。 |

### 复测后修正说明

1. 初版关于 Go 已有能力的判断继续成立：`approval.approve/reject`、`agent.package.publish`、`tool.provider.sync`、`prompt.preview`、Trace replay 等在源码和 OpenAPI 中都有证据。
2. 初版关于 PloyKit 调用错误/降级假成功的判断继续成立：`run.replay` 在 PloyKit 中被调用，但 Go command switch 未见；审批更新仍调用 `/v1/approvals/{id}`，而 Go 明确存在的是 command `approval.approve/reject`。
3. 初版关于 Go 真缺口的判断仍需 live 服务和登录态二次验证，尤其是 `/v1/runs`、`/v1/approvals`、`/v1/traces` list、`/v1/service-connections`、全局搜索、usage summary 等。
4. 本轮不能判定 PloyKit 业务 API 是否业务可用，因为 3000 API smoke 被鉴权拦截；需要用浏览器会话 cookie 或合法 API key 复测。
5. 本轮不能判定 Go live endpoint 的运行时状态，因为 8080 没有可访问服务；需要先启动 CleanCore 再跑 Go API smoke。

## 需要产品确认的问题

1. Skills 是全局技能库，还是 AgentPackage 内的 skill 子资源？
2. Members 指 workspace 人类成员，还是 Agent collaborators？
3. Service Connections 归 CleanCore 管理，还是归 PloyKit Host 管理？
4. API Keys 是调用 PloyKit 模块 API，还是直接调用 Go CleanCore？
5. Runtime replay 是只生成 trace replay 视图，还是要真实重放模型/工具调用？

## 最终判断

Go CleanCore 侧“确实缺”的主要是：全局搜索、统一分页过滤、run/approval/trace 列表读模型、run replay/cancel、service connections、usage summary/billing/quota、approval policies、export/report、saved views、batch actions。

Go CleanCore 侧“已经有但 Origin UI 没接”的主要是：AgentPackage draft/validate/review/publish/canary/stable/rollback、prompt preview、Agent 子资源（prompt-profile/tool-bindings/skills/collaborators/exported-tools/runtime-hooks）、ToolProvider/ToolManifest CRUD、ToolProvider governance、approval approve/reject、eval、trace replay、usage evidence。

因此，后续不能简单说“Go 那边缺很多”。更准确的拆法是：先把 PloyKit 本地假实现换成 Go 已有能力，再补 Go 真缺的读模型和产品能力。
## 三源码复核后的缺失与修改清单（module.ts / server.go / OpenAPI）

本节是对 `ploykit/modules/origin-agentops/module.ts`、`internal/server/server.go`、`docs/openapi.clean-core.v1.json` 三个文件重新逐项对照后的修正结论。结论不是“Go 端全缺”，而是分成三类：PloyKit 调用了错误路径、Go 端确实没有接口、Go 端已有但前端没有复用。

### A. P0：PloyKit 侧需要先改的错误调用

| 编号 | UI/动作 | 当前 PloyKit 调用 | Go / OpenAPI 实际能力 | 需要修改 |
| --- | --- | --- | --- | --- |
| P0-01 | 审批通过/拒绝 | `PATCH /v1/approvals/{approvalId}`、`DELETE /v1/approvals/{approvalId}` | Go 没有 `/v1/approvals/{id}` REST；但 `/v1/commands` 已支持 `approval.approve`、`approval.reject` | 先把 `resolveApproval` 和审批详情 API 改成 `/v1/commands`，按 `approve/reject` 分发 command；如果 UI 还要审批列表/详情，再补 Go 查询接口 |
| P0-02 | Run replay | `/v1/commands` + `run.replay` | Go command enum 没有 `run.replay`；Go 有 `/v1/traces/{trace_id}/replay` | 前端 replay 要么改成 trace replay，要么 Go 新增 `run.replay` command；当前写法不可用 |
| P0-03 | Run 详情/取消/等待输入 | `/v1/runs/{runId}`、`/v1/runs/{runId}/waiting-input` | Go 没有 `/v1/runs/*` REST；已有 `/v1/tasks/*`、`/v1/traces/*`、`task.command` | 明确 Run 是否等同 Task。若等同，应把 PloyKit 映射到 `/v1/tasks/{task_id}`、`/timeline`、`task.command`；若不是，Go 需要新增完整 `/v1/runs` |
| P0-04 | Trace 新建/编辑/删除 | `POST /v1/traces`、`PATCH/DELETE /v1/traces/{traceId}` | Go 只有 `/v1/traces/{trace_id}` 和 `/v1/traces/{trace_id}/replay` 能力，没有 trace 写入/删除 REST | UI 如果只是查看链路，应移除写操作；如果要保存回放、标注、删除，需要 Go 新增对应接口 |
| P0-05 | Service connections | `/v1/service-connections`、`/v1/service-connections/{id}` | Go / OpenAPI 未发现该资源 | 需要决定服务连接归属：如果是 Core 管外部服务凭据，Go 新增 CRUD、连通性检查、权限校验；如果是 Host 管理，前端不要转发到 CleanCore |
| P0-06 | Tools CRUD | `/v1/tools`、`/v1/tools/{toolId}` | Go 的工具清单资源是 `/v1/tool-manifests`、`/v1/tool-manifests/{tool_id}`；`/v1/tools/{tool_call_id}/trace` 只是调用链路 | PloyKit 工具页应改用 `tool-manifests`；不要把 tool manifest 当成 `/v1/tools` |
| P0-07 | Skills CRUD | `/v1/skills`、`/v1/skills/{skillId}` | Go 没有全局 `/v1/skills`；已有 `/v1/agents/{agent_id}/skills` | 如果 Skills 是 Agent 内资源，前端路径要带 `agent_id`；如果 UI 需要全局技能库，Go 需要新增全局 skills API |
| P0-08 | Agent 发布 | `/v1/commands` + `agent.package.publish`，payload 使用 `draft_version` | Go 支持 `agent.package.publish`，但发布逻辑需要 `draft_id`，或 `agent_id + version` | 前端发布参数需要改成 Go 接收的字段；否则会出现“前端本地标记成功、Go 未真正发布”的错觉 |

### B. P1：Go 端真实缺失，若 UI 设计保留就需要补接口

| 编号 | 缺失能力 | Go 当前情况 | 建议补法 |
| --- | --- | --- | --- |
| P1-01 | `/v1/runs` 运行实例资源 | 未发现 REST 资源 | 新增 list/detail/cancel/retry/replay/waiting-input，或正式把 Run 页面改为 Task 页面 |
| P1-02 | `/v1/approvals` 审批资源查询 | 只有 `approval.approve/reject` command，缺列表、详情、创建、删除、批量处理 | 新增 approvals 查询与管理 API；命令只负责状态流转 |
| P1-03 | `/v1/traces` 列表与写操作 | 只有单条 trace 读取与 replay | 新增列表、筛选、标注、导出、删除；如果 UI 不需要写操作，则删掉前端写入口 |
| P1-04 | `/v1/service-connections` 服务连接 | 未发现对应 OpenAPI 路由 | 新增连接 CRUD、连通性检测、密钥脱敏返回、审计记录 |
| P1-05 | 全局 `/v1/skills` | Go 当前是 Agent 子资源技能 | 新增全局技能库，或调整 UI 为“某 Agent 的 skills” |
| P1-06 | `/v1/search` 全局搜索 | 未发现对应路由 | 如 UI 有搜索框，需要补统一搜索；否则前端只做本地过滤并隐藏远程搜索预期 |
| P1-07 | 用量总览/趋势/配额 | Go 只有 `/v1/usage/evidence` | 若 UI 有 Usage 仪表盘，需要补 summary、timeseries、quota、cost breakdown |
| P1-08 | `/v1/api-keys` | Go 未发现该资源 | 若 API Key 属于 CleanCore，需要 Go 补 CRUD、scope、过期、吊销；若属于 Host，则前端不要转发到 Go |
| P1-09 | 批量导入/导出 | Go 多数资源只有单项 CRUD/command | 如 UI 有批量选择、导入、导出按钮，需要补 batch/import/export |

### C. 已有能力，前端应优先复用

| 能力 | Go / OpenAPI 已有 | 前端建议 |
| --- | --- | --- |
| AgentPackage 生命周期 | draft/create/patch/validate/review/publish/canary/stable/rollback 等 command 已有 | Agent 发布、回滚、评审页不要重新造接口，按 command 语义补齐字段 |
| Agent 子资源 | prompt-profile、tool-bindings、skills、collaborators、exported-tools、runtime-hooks 已有 Agent 子资源 API | 相关 UI 应挂在 `/v1/agents/{agent_id}/...` 下 |
| Tool provider/group/manifest | `/v1/tool-providers`、`/v1/tool-groups`、`/v1/tool-manifests` 已有 | Tools 页面优先改为 manifest/provider/group 三类资源 |
| Runtime hooks | provider、binding、preview、approval 相关接口已有 | Runtime hook UI 可直接对齐现有 API |
| Eval | eval suite/run 相关 command/API 已有 | 评测 UI 不应标为缺失，只需检查字段和返回结构 |
| Trace replay | `/v1/traces/{trace_id}/replay` 已有 | Replay 按 trace_id 调，不要调用不存在的 `run.replay` |
| Approval 状态流转 | `approval.approve`、`approval.reject` 已有 | 通过/拒绝动作复用 command，列表/详情另补查询接口 |
| Usage evidence | `/v1/usage/evidence` 已有 | 证据页可复用；统计看板仍需新增聚合接口 |

### D. 修改优先级建议

1. 先修 PloyKit 调错路径：approval、replay、tools、skills、publish payload。这些属于“已有能力没对上”，修复成本低，收益最大。
2. 再确认产品定义：Run 是否就是 Task，Skills 是否全局资源，API Key / Service Connection 归 Host 还是 Core。这里不确认就开写，容易做出两套重复模型。
3. 最后补 Go 真缺口：runs、approvals 查询、traces 列表/写操作、service-connections、usage 聚合、search、batch/import/export。
4. 每补一个接口，都同步更新 `openapi.clean-core.v1.json`，再回到 UI 页面做一轮接口实测，避免文档、Go、PloyKit 三边继续漂移。

### 4. 根据页面实测修正后的缺口判断

1. API Key、成员/RBAC 不应继续列为 Go Core 必补缺口。页面文案和实测请求都显示它们属于 PloyKit Host 能力。
2. 当前最严重缺口是 CleanCore 服务连接未配置/未运行：页面虽能展示，但所有核心数据处于降级模式。
3. 页面没有明显无限刷新，但 `state` 聚合过重：多数页面只拉一个大 state，导致每页都加载全部 Agent/Skill/Tool/Run/Approval/Audit 数据；后续数据量上来会有性能风险。
4. Action 层错误返回过粗：多种业务错误都被包装成 500 `MODULE_ACTION_ROUTE_ERROR`，UI 无法精确提示“资源不存在 / CleanCore 未接通 / command 不存在 / 参数不满足”。
5. Go Core 运行态尚未验证：本机缺 Go 工具链，Docker daemon 也未运行，所以 Go 接口“真实可用性”当前仍不能打勾。
